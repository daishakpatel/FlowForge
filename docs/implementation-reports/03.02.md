## 1. What was implemented

- **`cmd/flowforge-scheduler`:**
  - Loads config, then the logger.
  - Refuses to start on an old schema (`migrate.RequireLatest`).
  - Opens the pg pool and registers the metrics.
  - Starts a `LISTEN ff_scheduler_wake` waker.
  - Runs a `Runner` with `AlwaysLeader` and the `DecisionLoop`.
  - Serves `/metrics`, `/healthz` and `/readyz` on `FF_SCHED_HTTP_ADDR`.
  - Shuts down gracefully on SIGTERM or SIGINT.
- **`internal/scheduler`:**
  - **`Gate`:** `IsLeader`, `Epoch`, `Done`, and `Wait(ctx) error`.
  - **`AlwaysLeader`:** epoch 0; its `Done` never closes.
  - **`Loop`:** `Name` and `Run(ctx, gate)`.
  - **`Runner`:** `NewRunner` and `RegisterLoop`. It starts the loops on each new term and cancels them when `Done` closes, with no clock tick needed. It restarts them on the next term. A failing or panicking loop stops all loops, and `Run` returns its error.
- **`DecisionLoop`** (the task's `SchedulerLoop`, see §6):
  - **Wake-up:** it ticks every `FF_SCHED_TICK` and also wakes on `ff_scheduler_wake`.
  - **Run selection:** each tick takes up to 200 `CREATED`/`RUNNING` runs, round-robin by id. A short page wraps around to fill the tick, so no run is starved.
  - **One transaction per run:** each run is handled by `processRun` in its own transaction:
    - `AssertEpoch`, then lock the run (`FOR NO KEY UPDATE`).
    - CREATED → RUNNING.
    - PENDING → READY or SKIPPED, through `statemachine.EvaluateReadiness`.
    - READY → QUEUED within the limits, with the resolved input.
    - Once every head task is terminal, RUNNING → `DeriveRunStatus`.
    - `NOTIFY ff_task_queued`, delivered at commit.
  - **Status changes:** all of them go through `RunRepo.Transition` and `TaskRepo.Transition`. `INVALID_STATE`, and `CONFLICT` for a run, are treated as benign.
  - **Paused runs:** a `PAUSED` run is left alone; this is the seam for 03.05.
- **Head instances:** `ListHeadTasks` uses `NOT EXISTS` over `supersedes_task_id` within the run, bounded at 500 rows.
- **Limits:**
  - Per run: `concurrency.max_parallel_tasks` over the run's QUEUED+RUNNING tasks.
  - Per queue: `FF_QUEUE_LIMITS` over QUEUED+RUNNING tasks across all runs. A task from a full queue is passed over, so other queues still go.
  - Per tick: at most 100 promotions per run.
  - Order: `available_at`, then `created_at`, then `id`.
- **`InputResolver` seam:** the default is `IdentityResolver` (config verbatim). A resolver error moves the task READY → FAILED with no attempt, and its `task.failed` event carries `error_code: INVALID_INPUT`.
- **Metrics** (00E §11): `flowforge_scheduler_tick_duration_seconds`, `flowforge_scheduler_queue_depth{queue}`, `flowforge_tasks_total{status}`, `flowforge_workflows_started_total`, `flowforge_workflows_completed_total{status}` and `flowforge_workflow_duration_seconds`. They are applied only after a commit, so a retried transaction is never counted twice.
- **Wake-up from completions:** `workerapi.Service.Wake` sends `NOTIFY ff_scheduler_wake` in the transaction that finishes an attempt. `flowforge-api` wires it in.

## 5. Architectural decisions made during implementation

- **Decisions on one run are serialized.** `processRun` locks the run row (`FOR NO KEY UPDATE`) right after `AssertEpoch`. Without this, two concurrent calls could each count a different free slot and exceed `max_parallel_tasks`. `NO KEY UPDATE` still lets rerun rows referencing the run be inserted. Claims don't block on it, because the claim query locks only task rows.
- **A loop failure is fatal to the process.** A stale epoch, a returned error or a panic stops all loops, and the binary exits non-zero to be restarted (00C §10.1, fail safe). Per-run errors are logged and retried on the next tick. 04.07 can refine this for the Raft gate.
- **Notifications go inside the transaction.** `pg_notify` is called in the decision transaction, and in the worker's finish transaction, so it is delivered exactly at commit and never for a rolled-back change.
- **The definition cache is unbounded.** Definitions are immutable, so they are cached by id inside the loop. This is marked `shortcut:` in the code.
- **`flowforge_tasks_total{status}` counts only scheduler transitions** (READY, SKIPPED, QUEUED, FAILED). Worker-side statuses are counted by the API.
- **The scheduler binary reuses `workerapi.Waker`**, now with a channel parameter, instead of copying it.

## 6. Deviations from the specification

The `transitions_test.go` literal copy of `00E` gains the row. 00C §11 asks for test changes to be their own commit, but this one must ship with the code change to stay green, so they share a commit.
2. **`FF_SCHED_HTTP_ADDR` (`:8081`) and `FF_QUEUE_LIMITS`** (compatible extension). The task names `FF_QUEUE_LIMITS` and an obs server; `00E` §6 had neither. Both are recorded in `00E` §6, `.env.example` and `docs/configuration.md`, with the same `00A` amendment.
3. **Run order** (clarification). The task orders runs by `updated_at`, but `workflow_runs` has no such column (`00E` §2, which takes precedence). The same fairness comes from a round-robin by run id that wraps to fill a short page, with no migration needed.
4. **`SchedulerLoop` is named `DecisionLoop`** (clarification). `scheduler.SchedulerLoop` breaks 00C §8's no-stutter rule, and `Loop` is already the interface.
5. **Files outside the §7 list, and why:**
   - `persistence/repos.go`, `pg/scheduler_repo.go` and `sqlcgen`: the repository for the new queries, following the repo pattern.
   - `config/*`: the new variables.

   - `migrate.RequireLatest`: avoids copying the schema check into the second binary.
6. **Edited existing test:** `transitions_test.go` (item 1). No other existing test was changed.

## 7. Known limitations / follow-ups

- **`run_if: expr` stays PENDING.** Without an `ExprEvaluator`, such a task stays PENDING and a warning is logged every tick. 03.06 supplies the evaluator.
- **Not handled here:**
  - RETRY_WAIT → QUEUED, attempt timeouts and recovery (03.04).
  - Pause, resume and `cancel_requested` (03.05); a PAUSED run is only skipped.
  - The outbox relay that `config.Scheduler` mentions (03.07).
- **No leadership gauges yet.** `flowforge_scheduler_is_leader` and `flowforge_scheduler_epoch` (00E §11) are not registered; they come with the Raft gate in 04.07.
- **Two clocks in the duration metric.** `flowforge_workflow_duration_seconds` subtracts the database-clock `started_at` from the scheduler clock.
- **Queue-limit counts assume one leader**, which processes runs one at a time.
- **An unindexed query.** `CountActiveTasksByQueue` has no index for RUNNING rows. It runs only when `FF_QUEUE_LIMITS` is set; this is justified in `scheduler.sql`.
- **Package placement (follow-up).** The scheduler binary imports `internal/workerapi` for `Waker`. A small move of `Waker` to a shared package would remove that coupling.
- **Fuzz runtime.** About 34 s alone and about 70 s under `-race`; it is part of `make test-integration`.
- **Temporary stubs:** `AlwaysLeader` (until 04.07), `IdentityResolver` (until 03.06), a nil `ExprEvaluator` (until 03.06), and the PAUSED seam (03.05).
- **Defects found in earlier tasks:** none. The 02.03 follow-up ("share-lock test for 03.02") is closed by `TestScheduler_EpochShareLock`.
