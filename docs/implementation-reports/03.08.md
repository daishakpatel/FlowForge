## 1. What was implemented

- **Schedules (`internal/cron`).**
  - `Parse(spec, tz)` and `NextFire(spec, tz, after)` take a 5-field cron expression in an IANA timezone. The parser is robfig/cron v3, used as the parser only; tzdata is embedded.
  - **Rejected:** seconds, descriptors, `TZ=` prefixes, `Local`, and schedules that never fire, so fires are at least a minute apart.
  - **DST:** each wall-clock time fires once. A time in a spring-forward gap fires at the gap's end; a fall-back repeat fires on its first occurrence only.
- **`cron.Loop`** runs on the leader every 5 s. In one epoch-fenced transaction it locks the due triggers (`FOR UPDATE SKIP LOCKED LIMIT 50`). For each one:
  - **Within `FF_CRON_MISSED_GRACE`:** it starts the run through `Starter.StartFire` with key `cron:<trigger_id>:<fire_unix>` and the run's `trigger_id`, then advances to the next fire after the fire time.
  - **Later:** `skip` advances to the next future fire; `catch_up_one` starts one run for the oldest missed fire, unless it is older than the key-retention window, which is then a skip.
  - The advance is conditional on the old `next_fire_at`. Each fire or skip is audited (`system:cron`) in the same transaction.
  - **Failures:** a permanent start failure (the workflow is gone) is audited as an error and advanced; a transient one leaves the trigger due and is retried next tick.
  - The metric is `flowforge_cron_fires_total{outcome}`.
- **`service.TriggerService`.**
  - CRUD with validation: the workflow and version exist, the schedule parses, the timezone is valid, the input is an object, the name follows the workflow-name pattern.
  - `next_fire_at` is set on create, enable and schedule changes, and cleared on disable.
  - `StartFire` implements `cron.Starter` through `RunService.Start`. It resolves the latest version when none is pinned, and treats a key conflict as a replay.
- **REST:**
  - `POST /api/v1/triggers` (admin);
  - `GET /api/v1/triggers` and `/{trigger_id}` (viewer);
  - `PATCH /{trigger_id}` (admin);
  - `DELETE /{trigger_id}` (admin);
  - all in OpenAPI and the ACL, and audited by the middleware.
- **Wiring:** `cmd/flowforge-scheduler/wire_cron.go` registers the loop, and `flowforge-api` gets the trigger service. Config `FF_CRON_MISSED_GRACE` (60 s).

## 5. Architectural decisions made during implementation

- **DST by wall clock.** robfig's own `Next` walks wall-clock time in the zone and would double-fire a fall-back time and skip a spring-forward time. Each schedule is therefore evaluated on naive wall-clock time and mapped into the zone: the first occurrence, or the gap's end.
- **Layering.** `cron.Loop` depends on a small `cron.Starter`. `service.TriggerService` implements it, and `wire_cron.go` connects them, so the scheduler-side package never imports the API layer.
- **Atomic audit.** Audit rows for fires are written in the loop's transaction, atomically with the advance.
- **One broken trigger can't stall the rest.** A transient failure on one trigger doesn't fail the tick, so the loop's backoff can't make other triggers' fires late enough to be skipped.

## 6. Deviations from the specification

1. **Compatible extensions** (`00E` §6 and §11.1, `00A`):
   - `FF_CRON_MISSED_GRACE`;
   - `flowforge_cron_fires_total{outcome}` (outcome `fired`, `replayed`, `skipped`, `failed` or `retried`);
   - `TriggerRepo` and its types;
   - the failpoint `cron/after-start-before-advance`.
2. **Validation status** (a clarification): the task says "422/400", but `00E` §4 defines 422 only for `INVALID_WORKFLOW`, so trigger validation is `400 INVALID_ARGUMENT` with the field.
3. **The catch-up cap follows `FF_RETENTION_IDEMPOTENCY`** rather than a fixed 24 h (a clarification, from the code review): it's the same 24 h by default.
4. **Permanent start failures advance; transient ones retry** without failing the tick (a clarification).
5. **`last_fired_at` is the fire time handled,** not the wall-clock time of the start (a clarification).
6. **Changed tests:** the contract harness's sample path gains `{trigger_id}`.
7. **Files outside §7:** `internal/persistence` (repo and views), `rest/{router,routes_acl}.go`, `internal/config`, the `cmd/flowforge-api` main, `failpoint.go`, `Makefile`, `go.mod`. All of them are needed to implement and wire the task.

## 7. Known limitations / follow-ups

- **One fire per trigger per tick** (5 s), and up to 50 due triggers per tick.
- **Locks are held while runs start.** The loop's transaction holds the batch's trigger locks while each run starts in its own transaction (the task's design). A slow batch delays PATCH and DELETE on those triggers.
- **No index on `next_fire_at`.** The table is small.
- **Code review findings not fixed:** the trigger-name regex duplicates `dag`'s workflow-name pattern; and a fire reads its definition twice, once to resolve the version and once in `RunService.Start`. Both are minor.
- **Clock note.** The loop compares the API-stamped `next_fire_at` with its own clock; production hosts are NTP-synced, which is negligible against a 60 s grace.
- **Temporary stubs:** none.
- **Defects found in earlier tasks:**
  - **What:** 03.01's `TestPollTask_LongPoll` is flaky. About 1 run in 10 (`go test -race -count=10 -tags 'integration failpoint' -run TestPollTask_LongPoll ./internal/workerapi/`) the long poll answers about 1 s after the NOTIFY, the waker's fallback re-check, instead of within 200 ms.
  - **Not caused by this task:** it reproduces at `2489f9c`, before 03.07 and 03.08.
  - **Not fixed here:** it is outside this task's scope. It needs its own investigation of whether the wait is registered before the NOTIFY.
  - **Follow-up:** fix as `fix(03.01)` before the 03.09 gate.
- **Code review (`medium`) findings fixed:**
  - `Next` gave up inside a fall-back repeated hour, which stopped every-few-minutes triggers for good (confirmed by test, now covered);
  - the silent stop when a schedule ends;
  - the catch-up cap tied to key retention;
  - one broken trigger backing off the loop;
  - a PATCH could revert the loop's advance;
  - PATCH didn't normalize empty values;
  - a non-key CONFLICT was read as a replay.
