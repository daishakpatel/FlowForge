## 1. What was implemented

- **Protos** (`proto/coordination/v1`):
  - `kv.proto`, per `00E` §5.1:
    - **Services:** `KV` (`Get`, `Put`, `Delete`, `List`, `CAS`, `Txn`, `LeaseGrant`, `LeaseKeepAlive`, `LeaseRevoke`, `IncrCounter`) and `Cluster` (`Status`, `Health`).
    - **Types:** `Consistency` (`LINEARIZABLE`/`SERIALIZABLE`), `RequestMeta{client_id, request_id}`, `KeyValue{key, value, version, mod_index, lease_id}`, and `Compare`/`Op`/`OpResult` for `Txn`.

  - `raft.proto`: `RaftPeer.Stream(stream Envelope) returns (stream Envelope)`. An `Envelope` carries a marshalled `raftpb.Message` and `from`/`to`/`cluster_id`; snapshots travel as `SnapshotChunk`s of at most 1 MiB.
  - Generated Go is in `internal/gen/proto/coordination/v1`. `buf lint` is clean.
- **Dependencies:** `go.etcd.io/raft/v3` v3.7.0 (ADR-002's preferred path resolved) and `go.etcd.io/bbolt` v1.5.0, recorded in `versions.md`.
- **`internal/raftkv/storage`:**
  - **`Storage`:** `raft.Storage` plus `Save(hs, ents, snap)`, `SaveSnapshot`, `LoadSnapshot`, `Compact` and `Close`, with `MemoryStorage`'s semantics. Where `MemoryStorage` panics, these return errors.
  - **`Bolt`** (`OpenBolt(path, Identity)`):
    - **Layout:** buckets `meta` (`identity`, `hardstate`, `confstate`, `compacted`, with `applied` reserved for 04.03), `entries` (big-endian index → `raftpb.Entry`) and `snap` (`meta`, `data`).
    - **Writes:** each write method is one fsynced bbolt transaction (`NoSync: false`).
    - **On open:** the invariants are validated (`ErrCorruptStorage`, naming the problem), and the stored identity is checked (`ErrIdentityMismatch`).
    - **Before commit:** writes that would leave state raft can't restart from are refused (`ErrBrokenInvariant`).
  - **`Mem`** (`NewMem()`) wraps `raft.MemoryStorage` with the same checks. All methods hold its lock, and values are copied in and out.
  - **Other errors and limits:** `ErrLogGap`, `ErrCompactBeyondSnapshot`, `ErrSnapshotTooLarge`, `MaxSnapshotBytes` (64 MiB).
  - **`storagetest.Run(t, factory)`:** an 11-case conformance suite run against both implementations, and against `Mem` as the library reference.
- **Docs:** `docs/architecture/raft-storage.md` covers the contracts, interface, layout, Ready-loop order, crash-safety argument, evidence, performance and limits. It is linked from `README.md`.

## 5. Architectural decisions made during implementation

- **`Save` order:** install the snapshot, append the entries, write the hard state, all in one transaction, checked as a whole. That is the persistence step of the Ready contract (ADR-002).
- **`SaveSnapshot` is separate from `Compact`.** The node snapshots at its applied index and trims later, keeping trailing entries (`00E` §5.3 keeps 1 000). That makes "snapshot save + log truncation transactional" hold where both happen together: installing a leader's snapshot through `Save`.
- **Writes are refused when they break raft's restart invariants** (`ErrBrokenInvariant`; a code-review finding). Without that, `Bolt` could write a file its own `OpenBolt` refuses, or one that makes `raft.RestartNode` panic. The rules: the hard-state term is at or after the last entry's term; the commit lies between the compaction marker and the last index; and `SaveSnapshot` takes only committed indexes.
- **`Compact` stops at the latest snapshot.** Otherwise, after a restart, the entries in between could be recovered from neither.
- **Hot reads touch only the 16-byte marker and the last key.** Snapshot metadata is decoded only on the write paths.
- **The crash test re-runs the test binary as its child**, under the `integration` tag, so `make test` stays fast.

## 6. Deviations from the specification

All of these are clarifications:

- **`raft.Storage` signatures:** v3.7.0's `raft.Storage` takes and returns pointers (`*pb.HardState`, `[]*pb.Entry`, `*pb.Snapshot`), and `raftpb` is built on `google.golang.org/protobuf`. `Storage.Save` uses the same pointer types.
- **The version-conflict error reason is `CONFLICT`, not the task's `VERSION_MISMATCH`.** `00E` §4 defines version conflicts as `CONFLICT` (gRPC `ABORTED`) and outranks the task file (`00C` §2.12). The proto comment records the mapping.
- **Service names:** the task's `KV`, `Cluster` and `RaftPeer`, and the `Envelope` type in both directions, break buf's `STANDARD` naming rules. They are kept, with per-file ignores in `buf.yaml`, as for `worker.proto` in 03.01.
- **CAS delete:** `CASRequest.action.delete` is an empty `CASDelete` message, not a bool, so an invalid `delete=false` can't be expressed (a review finding, made before the contract ships).
- **Snapshot data is a blob in `snap/data`.** The task allowed a "path/blob"; the blob was chosen, bounded by `MaxSnapshotBytes` (64 MiB), as the task's own limit says.

## 7. Known limitations / follow-ups

- **Snapshot reads aren't cached.** `Bolt.Snapshot()` reads and copies the snapshot blob, up to 64 MiB, on each call. Raft calls it only to build a `MsgSnap`; if 04.02's transport retries often, cache the latest snapshot in `Bolt` (a review finding, deferred).
- **`InitialState`'s ConfState is the latest snapshot's,** as in `MemoryStorage`. That is adequate for 04.02's static membership.
- **`meta/applied` is reserved, not written.** 04.03 writes it with applied batches.
- **Synchronous throughput:** about 100 fsynced Readys a second on this machine (§3). 04.02 should batch entries per Ready.
- **`make proto-check` and `make sqlc-check`** pass only once the generated code is committed.
- **Not done:** porcupine tests (`00C` §11) are for the KV paths in 04.03 and 04.04; this task has no KV semantics yet.
