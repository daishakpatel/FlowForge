## 1. What was implemented

- **`workerapi.RetryOutcomeHandler`**, installed as the default `OutcomeHandler` in `flowforge-api`, `flowforge-scheduler` and the 03.04 tests:
  - It implements the decision table. Failed with retryable and the code not listed → RETRY_WAIT. Non-retryable, a listed code, or exhausted → FAILED. Timed out → RETRY_WAIT or TIMED_OUT. Abandoned → RETRY_WAIT or FAILED with `WORKER_LOST`. Abandoned attempts count toward `max_attempts`.
  - RETRY_WAIT sets `available_at = clock.Now() + NextRetryDelay`, with jitter from a seeded source behind a mutex, and records `task.retry_scheduled` with the delay.
  - A run with a cancel request gets CANCELLED instead of a retry; this is the guarded seam for 03.05.
- **`workerapi.AttemptEnder`:** the server-decided end of an attempt. A conditional, fenced attempt transition and then the `OutcomeHandler`, in one transaction, shared by the timeout and recovery loops. Ending an attempt that has already ended is a no-op.
- **RETRY_WAIT → QUEUED:** the `DecisionLoop` promotes RETRY_WAIT tasks whose `available_at` is at or before the clock's now, under the same budget and order as READY tasks, keeping their resolved input. The `ff_task_queued` waker fires.
- **`scheduler.TimeoutLoop`** (1 s): RUNNING attempts with `deadline_at <= $now` become TIMED_OUT (code `TIMEOUT`) through `AttemptEnder`, asserting the epoch, then wake the scheduler. Time spent QUEUED is not counted, as documented.
- **`recovery.Loop`** (2 s):
  - `LeaseProvider.Expired` → abandon each lost worker's RUNNING attempts → mark the worker LOST only if it is still ACTIVE and unseen → `worker.lost` in the outbox.
  - Fallback: RUNNING attempts whose worker is not in `LeaseProvider.Alive` and have been silent for 3×heartbeat + TTL are abandoned.
  - Liveness comes only from `LeaseProvider`.
- **Degraded behavior:**
  - **Shared loop body:** `scheduler.RunTicking` runs every loop.
  - **On failure:** the database being down makes `Once` return an error. The loop logs it, counts it in `flowforge_loop_errors_total{loop}`, and backs off with the tick doubled per failure up to 30 s.
  - **Stale epoch:** the loop stops.
  - **Transactions:** every decision is its own transaction.
- **Failpoint harness** (`internal/testutil/failpoint`):
  - `Inject` compiles away without `-tags failpoint`. With the tag, points are armed by `FF_FAILPOINTS=name=error|panic` or `Enable`, and `Hits` counts firings.
  - There are four points: claim (task RUNNING, attempt not yet inserted), `TaskRepo.Transition` (row updated, event not recorded), mid-`processRun` (readiness decided, promotion not run), and between the attempt ending and the outcome being handled.
- **`testutil.AssertInvariants(t, pool)`:**
  - no RUNNING task without a RUNNING attempt, and the reverse;
  - at most one RUNNING attempt per task;
  - `attempt_count` matches the attempts recorded;
  - every task's and run's status matches its latest event.
- **`testutil.Proxy`/`ProxyDSN`:** a TCP proxy a test can cut, to simulate the database going down.
- **Persistence:**
  - `persistence.RecoveryRepo` / `pg.RecoveryRepo` with `queries/recovery.sql` (overdue, per-worker and orphaned RUNNING attempts, and a conditional LOST mark).
  - `TaskMutation.AvailableAt`.
- **Wiring:**
  - `flowforge-scheduler` registers `TimeoutLoop` and `recovery.Loop` with the error metric, and reads `FF_WORKER_LEASE_TTL`/`FF_WORKER_HEARTBEAT`.
  - `flowforge-api` installs `RetryOutcomeHandler`.
  - `make test-crash` is added, and CI runs it after `test-integration`.

## 5. Architectural decisions made during implementation

- **`AttemptEnder` lives in `workerapi`,** next to the outcome semantics. The timeout and recovery loops share it, so "end an attempt, then decide its task" exists once and mirrors the worker-report path.
- **`RunTicking` is the shared body for all leader loops.**
  - A stale epoch stops the loop.
  - The database being down backs it off (tick × 2^failures, capped at 30 s) and counts the failure.
  - A failing item, such as one run or one attempt, is logged and counted but doesn't back the loop off. So one bad row cannot stall the scheduler.
- **The LOST mark comes last and is conditional:** only after every attempt is abandoned, and only if the worker is still unseen. A failure leaves the worker listed as expired, and a heartbeat that arrives meanwhile keeps it ACTIVE.
- **The fallback uses `LeaseProvider.Alive`**, not the task's "worker unknown" wording, so that liveness has a single source (AC 5). It also covers deregistered workers' leftovers.

## 6. Deviations from the specification

1. **Clock for a retry's `available_at`** (source conflict, settled by `00C` §2.12). ADR-021 uses the database clock; the task file uses `clock.Now()` and parameters from the injected clock. I followed the task through the additive `TaskMutation.AvailableAt`. Attempt deadlines remain on the database clock. Recorded in the `00A` amendment.
2. **Compatible extensions:**
   - `flowforge_loop_errors_total{loop}` and the allowed label `loop` (`00E` §11.1, `obs.AllowedLabels`);
   - `FF_FAILPOINTS` for test builds (`00E` §6, `docs/configuration.md`);
   - `FF_WORKER_LEASE_TTL`/`FF_WORKER_HEARTBEAT` now also read by the scheduler;
   - `persistence.RecoveryRepo`;
   - `make test-crash` and its CI step.
3. **Loop method name** (clarification). The loops' single-iteration method is `Once`, because `DecisionLoop` already has a `Tick` field. `DecisionLoop.tick` became `Once`, exported so the recovery tests can drive it.
4. **Claim failpoint placement** (clarification). The task says "after attempt insert before task transition", but 03.01's claim moves the task first and inserts the attempt second. The point sits between those two writes.
5. **Database outage** (clarification). The scheduler's database connection is cut through a TCP proxy (`testutil.Proxy`) for about 5 s, rather than stopping Postgres, which other tests share. The loops see the same refused and dropped connections.
6. **Files outside the §7 list:**
   - `persistence` (`RecoveryRepo`, `AvailableAt`, `recovery.sql`);
   - `workerapi/claim.go` and `complete.go` (failpoints);
   - `workerapitest` (clock and outcome options);
   - `testutil/invariants.go` and `proxy.go` (named in the handoff);
   - `obs/labels.go`, `config/scheduler.go`, `cmd/flowforge-api`, `Makefile`/CI.
   
   The changed existing tests are mechanical: `tick`→`Once` and `promotionOrder`'s new argument.

## 7. Known limitations / follow-ups

- **Two time bases.** Attempt deadlines are on the database clock while comparisons use the injected clock. In production both are NTP-synced host clocks, so the difference is skew.
- **Detection bound.** Worker loss is detected within lease TTL + 2 recovery ticks, not immediately.
- **Cancellation is a seam.** The retry handler honors `cancel_requested` only by not retrying; 03.05 implements cancellation.
- **Coverage.** `internal/recovery` is at 60.3 % (integration only), mostly in the error-logging branches.
- **`DecisionLoop.Once` is exported for tests and tools.** `Run` remains the production entry point.
- **Temporary stubs:** `PGLeaseProvider` remains the liveness source until 04.07 (Raft leases). That's expected, and `recovery.Loop` doesn't change when it does.
- **Defects found in earlier tasks:** none.
