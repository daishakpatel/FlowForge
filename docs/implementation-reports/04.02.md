## 1. What was implemented

- **`internal/raftkv/node`:** `Node` drives a `raft.RawNode` from one goroutine. Inputs arrive on bounded channels, so no raft state is shared.
  - **Why `RawNode` and not `StartNode`:** a `ManualTicker` can step it deterministically.
  - **Config:** `Config` takes the `00E` §5.3 defaults. `PreVote` and `CheckQuorum` are always on and proposal forwarding is disabled. `ParsePeers` parses the `FF_RAFT_PEERS` format `<id>=<host:port>`.
- **Ready loop** (`ready.go`):
  1. persist: one `storage.Save` per Ready, plus `Applier.Restore` for a leader's snapshot;
  2. send;
  3. apply committed entries in order, skipping those at or below `applied`: normal entries go to `Applier`, conf changes to `ApplyConfChange`;
  4. `Advance`.

  After applying, the loop snapshots every `SnapshotEntries` and compacts to `SnapshotTrailing`. A storage error stops the node (`Err`), and a library panic is recovered and stops it too.
- **Proposals** (`propose.go`):
  - **Framing:** each entry is framed with a unique proposal id (node, per-start nonce, sequence).
  - **Completion:** the waiter completes only once the entry is **applied** locally, and `Result{Index, Data, Err}` carries the Applier's result.
  - **Typed errors:** `NotLeaderError` (`ErrNotLeader`, with the leader's id and address), `ErrNoQuorum`, `ErrProposalDropped` (raft refused it, or a new leader overwrote the entry), `ErrProposalTooLarge` (more than `MaxSizePerMsg`), `ErrProposalTimeout` and `ErrNodeStopped`.
  - **Definite and unknown outcomes:** the definite errors are never applied; timeout and stop mean the outcome is unknown.
- **`ReadIndex`** (`readindex.go`): `RawNode.ReadIndex`, then wait until `applied ≥ index`.
  - **Failures:** `ErrNoQuorum` at once without a leader, `ErrReadIndexTimeout` on timeout.
  - **Lost requests:** raft never retransmits them, so unconfirmed reads are re-issued every election timeout.
- **Static membership:**
  - **First start:** an identical bootstrap on every node, a snapshot at index 1 with every voter in its `ConfState`.
  - **Later starts:** refused with `ErrPeersMismatch` when the peers differ from the persisted voters, or learners exist.
  - **Conf changes:** the `ApplyConfChange` path is wired, and the unexported `proposeConfChange` is tested.
- **Metrics:** `flowforge_raft_{is_leader,term,commit_index,applied_index,proposals_pending,peer_unreachable{peer},write_duration_seconds}`, registered through `obs.Registry`.
- **`internal/raftkv/transport`:**
  - **`GRPC`** implements `RaftPeer.Stream`:
    - one bounded outbound queue per peer (4 096), where overflow drops the message and calls `ReportUnreachable` (and `ReportSnapshot(failure)` for a `MsgSnap`);
    - reconnection with backoff;
    - `ReportSnapshot` feedback;
    - 1 MiB snapshot chunking and reassembly (`snapshot.go`);
    - inbound validation (cluster, node, sender);
    - an optional `Creds` hook for 09.01's TLS.
  - **`Fault`** wraps any sender with per-link and default drop, duplicate, delay (in ticks), reorder and partitions, and has a seeded deterministic mode.
- **`internal/raftkv/nodetest`:**
  - **`Cluster`:** an N-node in-process cluster over `Fault`, with manual ticks, `Stop`/`Start`/`Restart` from storage, `WaitLeader`, `CheckPrefixes`, `Converged` and an `OnSend` hook.
  - **`Recorder`:** an Applier that records every entry and flags any re-applied or out-of-order one.
- **Docs:** `docs/architecture/raft-node.md` (linked from `README.md`), and the `FF_RAFT_PEERS` format in `docs/configuration.md`.

## 5. Architectural decisions made during implementation

- **`RawNode`, not `raft.StartNode`:**
  - **Ownership:** one goroutine owns raft. Proposals, reads, inbound messages, transport reports and ticks are channel inputs.
  - **Test determinism:** a `ManualTicker` returns only after the node has drained its inbound queue, ticked, and handled the resulting Ready. Message latency in tests is therefore at most one round, so elections are independent of machine speed.
- **Conservative persist → send → apply order for every role** (rule 1). The leader's possible optimisation of sending in parallel with the write is not used.
- **Bootstrap through a snapshot `ConfState`, not `Bootstrap`/`StartNode` conf-change entries:**
  - **Uniformity:** every node writes the same snapshot at index 1 and hard state `{1, 1}`.
  - **Validation:** the persisted membership is always in `InitialState`, so validating the peer list at restart is a single comparison.
- **Proposal ids carry a per-start nonce** (`Config.Entropy`, seeded in tests). Entries from an earlier start, re-applied during restart, can't complete a new waiter with the same sequence number.
- **Definite and unknown errors** (`errors.go`):
  - **When a waiter fails definitely:** only when its entry can never apply. Raft refused it, or a different entry was applied at its index.
  - **What stays unknown:** proposals pending when a leader steps down, or covered by an installed snapshot. These end in a timeout.
  - **Why:** this removes the "failed but applied" ambiguity the task's §8 test asks about.
- **The Applier's error is part of `Result`, not `Propose`'s error.** It is the command's deterministic outcome, the same on every replica.
- **`Node.Step` never blocks** and drops when the inbound queue is full. The in-process network delivers synchronously from the sender's loop, so a blocking Step could deadlock two loops. Raft retransmits.
- **`ReportSnapshot` reports `SnapshotFinish` once the last chunk is written.** If the follower didn't install the snapshot, its next response makes the leader probe and resend. etcd's own transport reports at the same point.

## 6. Deviations from the specification

All of these are clarifications:

- **Applied-index persistence:** task §4 says "persist applied index in storage meta". The node instead takes the applied index stored with the FSM state to be the **latest snapshot's index**, as rule 5 says ("skip applying entries ≤ `applied` stored with the FSM state").
  - **Why:** the `Applier` interface's state lives in memory (`Snapshot`/`Restore`). Persisting a later applied index without that state would make a restart skip entries whose effects were lost.
  - **What stays unchanged:** `meta/applied` in Bolt stays reserved and unused, and the `storage.Storage` interface is unchanged.
- **`ErrProposalTimeout`, not `ErrTimeout`:** task §4 says `ErrTimeout`; §12's handoff list (the exact names) says `ErrProposalTimeout`. Two errors were added: `ErrProposalDropped` (§4: "dropped by raft … surface as retriable errors") and `ErrReadIndexTimeout`.
- **`Status()`, not `Leader()`/`Term()` accessors:** `Status()` returns `{ID, Leader, LeaderAddr, IsLeader, Term, Commit, Applied}`.
- **Fixed settings:** `PreVote` and `CheckQuorum` are fixed on (`00E` §5.3), not configurable. Library logging is fixed at WARN through the slog adapter.
- **`FF_RAFT_PEERS` entry format:** `<id>=<host:port>`. 01.03 left it to this task. The format is documented in `docs/configuration.md`; there is no new variable.
- **Restart test storage:** `TestCluster_RestartAllPreservesState` restarts from real bbolt files for seeds 1–3, and from `storage.Mem` for seeds 4–20.
  - **Why:** Bolt fsyncs every Ready, which takes about 3.5 s per seed here, so 20 Bolt seeds take 73 s.
  - **Equivalence:** Mem holds exactly what `Save` persisted and passes the same conformance suite.
  - **Not covered here:** crash durability of the file itself is 04.01's `TestBolt_CrashSafety`.

## 7. Known limitations / follow-ups

- **Dynamic membership** (FR-RAFT-11, optional) is not implemented beyond the wired `ApplyConfChange` path. Restart validation compares the snapshot's `ConfState` only, so conf changes still in the log would need log-aware validation.
- **`FF_RAFT_SNAPSHOT_ENTRIES`** (`00E` §5.3) is not yet a config key. `node.Config.SnapshotEntries` exists; 04.04's `flowforge-raft` binary maps the config. Follow-up: add the variable to `internal/config.Raft` when the binary is wired.
- **Elections aren't seed-reproducible:** the raft library's election jitter uses its own random source and can't be seeded. Seeds fix the fault decisions and nonces, and every seed also exercises a different election interleaving.
- **No reconnection jitter:** a node has two peers, so there is no herd to spread.
- **Snapshots are whole in-memory blobs** of up to 64 MiB (04.01), sent in chunks; `Bolt.Snapshot()` isn't cached (04.01's follow-up still stands).
- **Not done:** porcupine linearizability (`00C` §11) belongs to the KV paths in 04.03/04.04; this task has no KV semantics.
- **Code-review findings fixed** (all with tests):
  - the harness reused one proposal nonce across restarts (it now derives a nonce per start and fails on a reused one);
  - snapshot reports could be dropped (reports now coalesce per peer and are never dropped);
  - an oversized proposal could stall replication (`ErrProposalTooLarge`);
  - a lost ReadIndex request hung (it is now re-issued);
  - a failed snapshot was retried on every Ready (it now waits for another `SnapshotEntries`);
  - empty snapshot data was restored inconsistently;
  - a negative `TickInterval` was accepted;
  - a snapshot was deep-copied on every send;
  - unknown peer ids created metric series.
- **Declined, documented instead:** `Fault.Tick` reorders released messages with the default probability, not the link's.
- **Process deviation:** the gRPC transport (`grpc.go`, `peer.go`) was written before its tests, which departs from TDD. Its tests were then mutation-checked (removing the cluster-id check is caught).
- **Defects found in earlier tasks:** none.
- **Temporary stubs:** none.
