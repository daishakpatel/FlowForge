## 1. What was implemented

- **`cmd/flowforge-worker`:**
  - Loads config (`FF_WORKER_*`, `FF_API_GRPC_TARGET`, `FF_WORKER_TOKEN`) and registers the built-in handlers. `crash` is registered only with `FF_WORKER_ENABLE_CRASH_HANDLER=true`.
  - Dials the API.
  - Serves `/metrics`, `/healthz` and `/readyz` on `FF_WORKER_HTTP_ADDR`.
  - Runs the worker, and on SIGTERM or SIGINT shuts down gracefully and exits 0.
- **`internal/worker/handlers` (SDK):**
  - `Handler`, `TaskContext{TaskID, AttemptID, AttemptNumber, IdempotencyKey, Input, Deadline, Logger, RunID, Traceparent}`.
  - `Registry` with `NewRegistry`, `Register` (an empty or duplicate type is an error), `Get` and `Types`.
  - Errors: `Retryable(code, err)` and `NonRetryable(code, err)`, both of type `*Error`. `Classify` maps an unclassified error to retryable `HANDLER_ERROR`, `context.Canceled` to `CANCELLED`, and a deadline to `DEADLINE`.
  - `Execute` recovers a panic into a retryable `PANIC`. The stack goes to the attempt log only.
  - Built-in handlers: `noop`, `sleep`, `fail`, `flaky`, `echo` and `crash`. `crash` exits through an injected function; `os.Exit` in the binary.
- **`internal/worker/runtime`:**
  - **Connection:** `Dial` opens a plaintext gRPC connection with bearer credentials and reconnect backoff from 100 ms to 5 s.
  - **Construction:** `New(Config, Deps)` and `Worker.Run(ctx)`.
  - **Registration:** `Register` runs on start. Startup retries while the API is unreachable and returns an error on rejection. After any unreachable or not-registered answer, the worker registers again before its next poll or heartbeat.
  - **Polling:** the poll loop asks only for `capacity − running` tasks.
  - **Attempts:** each runs in its own goroutine, under a context that ends one second before the server's deadline. That context is cancelled by heartbeat `cancel_attempt_ids` (reported `CANCELLED`), by `stale_attempt_ids` (result dropped), and by shutdown (reported `WORKER_SHUTDOWN`, retryable).
  - **Heartbeats:** the heartbeat loop runs in its own goroutine and shares no lock with handlers.
  - **Reports:** `CompleteTask`/`FailTask` carry the fencing token, and are retried with bounded exponential backoff and jitter while the API is unreachable, up to the attempt deadline. `STALE_ATTEMPT` is never retried.
  - **Logs:** a per-attempt `slog` handler writes to a bounded buffer that drops the oldest line first and counts drops. The buffer is shipped in one `ShipLogs` stream before the outcome is reported.
  - **Shutdown:**
    - Polling stops; an in-flight poll is allowed to return.
    - Attempts get the grace period.
    - Any still running are cancelled, and their reports get another 10 s.
    - Heartbeats stop, and the worker deregisters.
  - **Metrics:** `flowforge_worker_active_tasks`, `flowforge_worker_task_outcomes_total{outcome}`, `flowforge_worker_log_lines_dropped_total` and `flowforge_worker_lease_renewal_failures_total`.
- **`internal/workerapi/workerapitest`:** a reusable test server. It is the real `WorkerService` with production interceptors, repositories and waker, on a fresh database. It listens on a loopback address that survives `Restart`, counts calls per method, and has `Queue` and `Wait*` helpers. The worker tests use it, and so can 03.09.

## 5. Architectural decisions made during implementation

- **Logs are shipped once, when the attempt ends,** just before the outcome is reported. They are not streamed live. This keeps one bounded buffer per attempt and one stream per attempt, and the buffer size (1000) matches the server's per-attempt cap.
- **Attempts outlive the poll context deliberately.** An attempt keeps the poll context's values but not its cancellation. Shutdown cancels attempts through the running set (`cancelAll`), and reports use a separate context that ends at the attempt deadline or the shutdown cut-off.
- **Re-registration is lazy.** It is triggered by any unreachable or `INVALID_STATE` answer and done before the next poll or heartbeat; it does not watch the connection state. Registration persists in Postgres across API restarts, so this also covers a lapsed or deregistered worker.
- **`crash` exits through an injected function.** Library code never calls `os.Exit`.
- **The crash handler is rejected under `FF_ENV=prod`,** because it lets anyone who can start a run kill a worker.

## 6. Deviations from the specification

1. **New configuration and metrics** (compatible extension). The task names "task outcome counters" and counted log drops, and a worker's metrics need a listener; `00E` had none of these. Added:
   - `FF_WORKER_HTTP_ADDR` (`:8082`);
   - `flowforge_worker_task_outcomes_total{outcome}`;
   - `flowforge_worker_log_lines_dropped_total`.

   `FF_WORKER_SHUTDOWN_GRACE` and `FF_WORKER_ENABLE_CRASH_HANDLER` are named by the task and are now in `00E` §6. All of this is recorded in `00E` with a `00A` amendment.
2. **Shutdown cancellation is reported as `WORKER_SHUTDOWN`, retryable** (clarification). The task specifies `CANCELLED`/non-retryable only for cancellation by the server, and says only "report outcomes" for shutdown. A worker going away must not permanently fail a task.
3. **Two new worker-side error codes** (clarification): `INVALID_RESULT` (non-retryable) for a result that is not valid JSON, and `DEADLINE` (retryable) for a handler that overruns the courtesy deadline. Both are handler-level codes in `task_attempts.error_code`, not `00E` §4 API codes.
4. **Shared test server.** `internal/workerapi/workerapitest` is outside the §7 file list. The runtime and binary tests both need a restartable real API, and 03.01's test helper is private to its package and uses bufconn. Duplicating it would break 00C §2.1.
5. **The logs test reads through the repository.** It reads with `TaskLogRepo.List`, the exact query the `GET /api/v1/attempts/{id}/logs` handler serves, rather than over HTTP. 02.05/03.01 already contract-test that route.

## 7. Known limitations / follow-ups

- **Defects found by the stress run and fixed in this task:**
  - **Lost claims at shutdown.** Cancelling an in-flight `PollTask` at shutdown could drop a response carrying tasks the API had already claimed and committed, orphaning those attempts as RUNNING until recovery. Shutdown now lets the in-flight poll return, bounded by poll wait plus RPC timeout, and starts what it returned. The cost is that shutdown can take up to one poll wait (10 s) longer.
  - **Outage not counted.** While re-registration was failing, heartbeat ticks were skipped without being counted, so `flowforge_worker_lease_renewal_failures_total` stayed at 0 through an API outage. Such ticks are now counted.
  - **Test race.** One test read the outcome counter before the worker had received the API's answer; it now waits for the counter.
- **Logs appear only at the end.** A long attempt's logs appear only when it ends, and a crashed worker's buffered lines are lost.
- **Plaintext transport**, matching the API's gRPC port; TLS comes with deployment hardening.
- **`/readyz` doesn't check the API.** It reports only that the process serves; that the API is reachable shows in registration, the metrics and the logs.
- **Retries happen in 03.04.** Until 03.04's `OutcomeHandler` lands, a retryable failure still fails the task, because `TerminalOutcomeHandler` does no retries. The worker reports retryability correctly for 03.04 to use.
- **Wired later:** `cancel_attempt_ids` is fed by 03.05's `CancelSource`; recovery of attempts abandoned by a crash or shutdown cut-off is 03.04.
- **Temporary stubs:** none new.
- **Defects found in earlier tasks:** none.
