## 1. What was implemented

- **The Raft fault suite** `test/fault/raft` (build tag `fault`) has 22 scenarios:
  - **the twelve of v1.0 §8.7:**
    1. kill the leader;
    2. kill a follower;
    3. restart a follower;
    4. kill two nodes;
    5. restore a stale data directory;
    6. network delay;
    7. a 1|2 partition;
    8. restart all nodes;
    9. writes without quorum;
    10. state-machine consistency after recovery;
    11. snapshot restore of a wiped node;
    12. a stale scheduler cannot act after a new epoch;
  - **five extras:** X1 rolling restart under load, X2 leader transfer under load, X3 clock skew, X4 slow disk, X5 large snapshot install under load;
  - **the negative control N;**
  - **four container-level scenarios:** C1 kill the leader, C2 pause the leader, C7 partition (network disconnect), C8 restart all.
- **Every scenario** declares its injected fault and expected behaviour in code, and asserts the expected behaviour explicitly. It also:
  - runs a seeded 4-client load and checks its history with Porcupine, archived on a violation;
  - measures time-to-recover as the first successful linearizable write after the fault;
  - compares that with the 00_MASTER §6.1 targets;
  - ends by checking that every node converged to one state hash at one applied index;
  - appends one JSON row to `FF_FAULT_RESULTS`.
- **The negative control:** a client deliberately takes a serializable read from a partitioned follower and records it as a linearizable read. Porcupine must judge that history Illegal, which proves the checker can fail.
- **Levels:**
  - **In process:** `internal/raftkv/kvtest`, the full stack over loopback gRPC, at the production timing (100 ms ticks, 1 s election timeout).
  - **Container:** the Compose `raft-1..3` through the new `test/fault/dockerctl` (`docker compose kill`, `pause`, `restart`, `docker network disconnect`).
- **`kvtest` gains test-harness options:**
  - `Options.Faults` and `FaultSeed`: 04.02's `transport.Fault` around each member's transport, driven by `Partition`, `Heal` and `SetFaults`, with a fault ticker;
  - `Options.MemberClock`;
  - `Options.WrapStorage`;
  - `Cluster.Backup` and `Restore`.
- **The renderer `scripts/chaos/render-fault-report.go`** (unit-tested):
  - folds the runs into `docs/testing/raft-fault-results.json` and `raft-fault-report.md`, with each scenario's pass count and its time-to-recover min / median / max;
  - judges each target over every run;
  - fails a scenario that reported fewer runs than expected;
  - appends the hand-written analysis (`raft-fault-notes.md`).
- **Make and CI:**
  - `make test-fault-raft`: `FAULT_RUNS` (default 5) consecutive runs, then the report; `FF_FAULT_CONTAINERS=1` adds the container scenarios;
  - CI (`go.yml`) runs the in-process scenarios once;
  - `nightly.yml` runs everything five times and uploads the report and any Porcupine artifacts.
- **Docs:**
  - `docs/testing/fault-injection.md`: how to run it, how it works, how to add a scenario;
  - the committed report and its analysis.

## 5. Architectural decisions made during implementation

- **Network faults at container level** use `docker network disconnect` (task §5: "pick one and document"). Latency is injected only in process (`transport.Fault`, seeded). There is no Toxiproxy service.
- **Two levels.** In process is the CI default: fast, deterministic schedules, and it can reach a minority node or skew a clock. Container level is nightly: production binary and image, the real timing, and real process kills and pauses.
- **Time-to-recover** is the first successful linearizable write after the fault, probed every 20 ms with 1 s writes. Targets are declared before the fault, so a run that never recovers counts as a miss.
- **Key prefixes are unique per scenario and per run,** because the Compose cluster keeps its data.
