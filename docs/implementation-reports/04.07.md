## 1. What was implemented

- **`FF_COORDINATION=local|raft`** for `flowforge-api` and `flowforge-scheduler` (`local` is the default and the previous behaviour), plus `FF_SCHED_NODE_ID`. In raft mode the config requires `FF_WORKER_LEASE_TTL` ≥ 3 s, 3× the Raft election timeout.
- **Scheduler (raft mode):** `cmd/flowforge-scheduler/wire_coordination.go`.
  - **Election:** a `coordination.Elector` over the Raft client campaigns under `FF_SCHED_NODE_ID`, and its `Gate` gates every registered loop: decision, timeout, recovery, cron, outbox relay and retention.
  - **Fencing:** `coordination.PGFence` (`internal/coordination/pgfence.go`) activates each won epoch with `ClusterRepo.SetEpochIfGreater` and records `scheduler.leader_changed` in the same transaction, before the term starts.
  - **Liveness:** recovery reads it from `RaftLeaseProvider`.
  - **Deposed:** a deposed scheduler that hits STALE_EPOCH exits; this is the existing `Runner` contract.
- **API (raft mode):** `cmd/flowforge-api/wire_coordination.go`.
  - **`workerapi.RaftLeaseProvider`** (`internal/workerapi/lease_raft.go`):
    - Register and Renew write Postgres, then Raft;
    - a Raft failure other than a conflict degrades: logged, counted in `flowforge_worker_lease_renewal_failures_total`, and the heartbeat still succeeds; Raft calls there are bounded at 2 s;
    - the first heartbeat after an outage restores the lease;
    - `Expired` = no live Raft lease **and** not seen in Postgres within the TTL, and a failed Raft read is an error (recovery abandons nothing);
    - `Alive` = ACTIVE workers with a live Raft lease.
  - **`worker.registered`** is recorded on every successful `Register` (`Service.Events`).
- **`GET /api/v1/cluster/status`** (viewer; `internal/api/rest/cluster.go`, OpenAPI `ClusterStatus`, ACL):
  - the content: coordination mode, scheduler leader, epoch and since (leader key), the fenced epoch (Postgres), Raft availability, term, commit and the leader's view of every node, and live workers;
  - each part is read concurrently and bounded at 2 s, and a failed part is null.
- **The AssertEpoch coverage guard:** `internal/testutil/epochguard`.
  - **How it works:** a `TxManager` interceptor that fails a test when a guarded transaction does not start with the epoch lock.
  - **Where it runs:** around the leader loops of the scheduler, recovery, outbox and cron integration suites.
  - **Its own test:** `TestEpochGuard_CatchesAWriteWithoutAssertEpoch` proves it fails on an injected unfenced write.
- **Compose:**
  - `flowforge-migrate`, `flowforge-api`, `scheduler-1..3`, `worker-bootstrap` (creates the workers' key) and `worker-1..2`, in profiles `raft` and `full`; `make failover-up` = `--profile core --profile raft`;
  - `deploy/docker/Dockerfile.service` builds every Go service from the 04.06 pattern.
- **e2e:**
  - the harness runs either mode (`FF_E2E_COORDINATION`, `make test-e2e-raft`) and starts a 3-node `flowforge-raft` cluster per test;
  - `test/e2e/raft_failover_test.go` covers leader kill, paused leader, worker kill and quorum loss.
- **Docs:** `docs/architecture/leadership-and-fencing.md`; the runbooks `docs/runbooks/scheduler-failover.md` and `docs/runbooks/worker-unavailable.md`.

## 5. Architectural decisions made during implementation

- **`Expired` in raft mode is Raft expiry AND Postgres staleness.** Raft remains necessary; the Postgres condition prevents the post-outage spurious abandonment the task forbids.
- **A deposed scheduler exits on STALE_EPOCH** (the existing `Runner` contract); Compose restarts it as a candidate.
- **The guard rule is "the first statement is the epoch lock",** matching `ClusterRepo.AssertEpoch`'s documented contract. Retention is exempt: no transaction, no decision.
- **The leader timing in the demo and e2e is 6 s / 2 s** (§6). The defaults stay 10 s / 3 s.

## 7. Known limitations / follow-ups

- **Defects found in earlier tasks:**
  - **02.04, fixed (separate commit):** `rest.classify` mapped a pooled connection dropped by the server (SQLSTATE 57P01 or class 08) to 500 INTERNAL instead of 503 UNAVAILABLE with Retry-After (00_MASTER §6.2).
    - **How it showed:** `TestContract_API` failed once cluster status, which reads Postgres concurrently, left two idle connections in the pool. Captured error: `*pgconn.PgError` 57P01.

  - **04.05, fixed (separate commit; the code review found it):** `WorkerRegistry.Register` revoked leases with `context.WithoutCancel`, so a Raft hiccup stretched a bounded caller to the client's 10 s default. The revokes now have their own 1 s bound (`TestRegistry_RevokeNeverOutwaitsTheCaller`).

- **A deposed scheduler exits** and relies on a restart policy.
- **The single-leader belief assumes bounded clock-rate drift** (04.05); the fence makes a violation harmless.
- **`/api/v1/workers` still derives LOST from Postgres** in both modes; liveness in raft mode is visible in `cluster/status.workers.alive`. A follow-up could show the Raft view there.
- **`worker-bootstrap` creates a new worker key on every Compose start** (dev only).
