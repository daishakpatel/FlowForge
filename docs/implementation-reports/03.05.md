## 1. What was implemented

- **REST (operator):** `POST /api/v1/runs/{run_id}/cancel[?force=true]`, `…/pause` and `…/resume`. They're backed by `RunService.Cancel`, `Pause` and `Resume`, documented in OpenAPI, entered in the ACL table, and audited by the existing middleware. Each answers `200` with the run:
  - cancelling twice, or cancelling a CANCELLED run, returns it unchanged;
  - pausing a PAUSED run is a no-op;
  - cancelling a SUCCEEDED or FAILED run, pausing anything other than RUNNING, and resuming anything other than PAUSED are all `409 INVALID_STATE`.
- **Cancel:**
  - The API sets `cancel_requested`, pulls `deadline_at` in to `now + FF_CANCEL_GRACE` (`now` with force), and wakes the scheduler.
  - `processRun` cancels every head task that hasn't started (PENDING, READY, QUEUED, RETRY_WAIT). RUNNING tasks are cancelled cooperatively: `workerapi.RunCancelSource` returns their attempt ids in heartbeat answers, and the worker reports `FailTask(CANCELLED)`, which the API now records as attempt CANCELLED, with the task CANCELLED.
  - At the deadline, `TimeoutLoop` force-cancels the remaining RUNNING attempts through the fenced `AttemptEnder`.
  - Once every head task is terminal, the run is CANCELLED, from CREATED, RUNNING, PAUSED or NEEDS_ATTENTION.
  - `RetryOutcomeHandler` turns any outcome other than success in a cancel-requested run into CANCELLED.
- **Pause and resume:** RUNNING ⇄ PAUSED. A paused run gets no promotions and no requeued retries, and `PollTask` already skips it. Running attempts complete normally. Resume wakes the scheduler.
- **Workflow timeout:** at start the scheduler sets `deadline_at = now + timeout_seconds`, through a new `RunTransitionParams.DeadlineAt`. `TimeoutLoop` ends RUNNING or PAUSED runs past their deadline: it force-cancels RUNNING attempts, cancels the rest, and fails the run with `run.failed` reason `WORKFLOW_TIMEOUT`. A cancel-requested run past its grace ends CANCELLED instead.
- **Persistence:** `queries/runcontrol.sql` with `persistence.RunControlRepo` / `pg.RunControlRepo`. `ListActiveRunIDs` also returns cancel-requested PAUSED and NEEDS_ATTENTION runs.

## 5. Architectural decisions made during implementation

- **A cancel shortens the deadline.** The run's `deadline_at` becomes `min(deadline, now + grace)`, or `now` with force. So `TimeoutLoop` is the single enforcement point for workflow timeouts and for the end of a cancel's grace. No column, migration or second timer is needed, and the decision is crash-consistent because it's just a row value.
- **The scheduler sets the workflow deadline at start,** from its injected clock, the same base `TimeoutLoop` compares with.
- **Locking.** Pause and resume use the run's version (optimistic) and retry on `CONFLICT`. Cancel is a conditional `UPDATE`. The scheduler's run lock serializes it against decisions.
- **Pausing a cancel-requested run is `INVALID_STATE`,** so the cancel cannot be held up.

## 6. Deviations from the specification

1. **Compatible extensions** (`00E` + `00A` amendment):
   - the run transitions CREATED → CANCELLED, PAUSED → CANCELLED and PAUSED → FAILED (§3.3);
   - `FF_CANCEL_GRACE` (§6);
   - `run.failed` gains an optional `reason`;
   - `RunTransitionParams.DeadlineAt`;
   - `RunControlRepo`.
2. **Resume isn't idempotent** (clarification). Task §4 calls all three endpoints idempotent, but §8 says resume of RUNNING → 409. I followed §8: pause and cancel are idempotent, resume of a non-PAUSED run is 409.
3. **The deadline is set at start** (clarification). `InsertRun` (02.03) still sets a creation-time deadline; the start overrides it with `started_at + timeout_seconds`, as the task asks.
4. **Changed existing tests:**
   - `transitions_test.go`: the `00E` §3.3 copy gains the three transitions. The case asserting CREATED → CANCELLED has no event now expects `run.cancelled`; the "disallowed transition" check moved to SUCCEEDED → RUNNING.
   - 03.03's `TestWorker_ServerCancellation`: a worker-reported cancel now leaves the attempt CANCELLED (code CANCELLED, not retryable) instead of FAILED, as 03.05 §4 specifies.
   - `api_integration_test.go`: the env's `RunService` gains the run-control fields, and new cases cover the operations.
5. **Files outside §7:** persistence (queries, repo, `DeadlineAt`), `statemachine`, `events`, `config`, both `cmd` mains, the `workerapi` complete and outcome files, `router.go`/`routes_acl.go`, and the test files listed in §2. All of them are needed to implement and wire the task.

## 7. Known limitations / follow-ups

- **Forced cancellation has a lag:** up to one `TimeoutLoop` tick (1 s) after the grace.
- **Handlers that ignore `ctx`** keep running on the worker after a cancel. Their attempt is still ended at the grace, and their report rejected.
- **A cancelled run's `deadline_at` shows the grace's end,** not the original workflow deadline.
- **The cancel grace is the API's setting.** The scheduler doesn't read `FF_CANCEL_GRACE`.
- **Temporary stubs:** none new. The `CancelSource` stub (`NoCancels`) is replaced in the API by `RunCancelSource`.
- **Defects found in earlier tasks:** none.
