## 1. What was implemented

- **`flowforgectl`** (`cmd/flowforgectl`, stdlib `flag`):
  - All the commands the task lists: `workflows create|list|get`; `runs start|get|tasks|events|logs|watch|cancel|pause|resume|rerun|retry`; `workers list`; `triggers create|list|enable|disable`; `api-keys create|list|revoke`.
  - Configuration: `FF_API_URL` and `FF_API_KEY`. Output: `-o table|json`.
  - Exit codes: 0 for success; 1 for an API or network error, with the error envelope printed; 2 for a usage error.
  - List commands follow `next_cursor`.
  - `runs watch` consumes SSE from the run's first event. It resumes with `Last-Event-ID` after a drop, or after 45 s of silence (a half-open connection). It stops at `run.succeeded`, `run.failed`, `run.cancelled` or `run.needs_attention`.
  - The client is hand-written, with generic JSON values: no generated OpenAPI types exist.
- **E2E harness** (`test/e2e`, tag `e2e`):
  - **Build and processes:** `TestMain` builds the api, scheduler, worker and CLI binaries once, with `-race`. `New(t)` starts a Postgres container per test and migrates it. `StartAPI`, `StartScheduler`, `StartWorker` and `StartAll` run the binaries as subprocesses on free ports and wait for `/readyz`.
  - **Faults:** `Kill`, `Stop`, `Restart`, `Pause` and `Resume` use SIGKILL, SIGTERM, SIGSTOP and SIGCONT. `PausePostgres` uses `docker pause` / `unpause`.
  - **Logs:** captured per process. On failure the harness prints each log's tail and dumps every task and attempt from the database. `FF_E2E_LOG_DIR` keeps the logs.
  - **Measurements:** `METRIC` lines record recovery times.
- **Scenario library:** each scenario is its own test with a fixture in `test/fixtures/workflows/`.
  - From the task's list: diamond across 2 workers; fan-out within capacity; retry-then-succeed; non-retryable failure; timeout; worker SIGKILL; SIGSTOP zombie; scheduler restart; API restart; DB pause of 5 s; cancel; pause/resume; rerun after failure with an `on_failure` branch; templating chain; cron firing; idempotent start; SSE consumption.
  - Added: a worker restarted under the same id; the CLI end to end, including the cyclic definition rejected with `CYCLE`; and the demo script.
- **Soak:** `TestSoakChaos` runs 500 runs × a 6-task DAG on 4 workers.
  - **Chaos:** from a seeded RNG (`FF_E2E_SEED`, logged). Every 10 s a random worker is SIGKILLed and restarted; every 30 s the scheduler is SIGKILLed and restarted.
  - **Requirements:** every run succeeds; no task has more than one `SUCCEEDED` attempt; `AssertInvariants` holds.
  - **Recorded:** the duration, kills, restarts and abandoned attempts.
- **Gate report, fixtures, demo:**
  - `docs/testing/phase3-gate.md`.
  - The `diamond`, `retry` and `market-data-skeleton` fixtures, plus nine more.
  - `scripts/demo/engine-demo.sh`; `TestDemoScript` runs it twice against a live deployment.
- **Build and CI:** `make test-e2e`; a CI `e2e` job that uploads logs on failure; lint covers the `e2e` tag.
- **Defects fixed in earlier tasks (§6.6):**
  - **Recovery (03.04):** an attempt of a worker restarted under the same id was never recovered before its deadline (§6).
  - **`TestPollTask_LongPoll` flake (03.01):** the test env didn't wait for LISTEN. The env now waits, after its cleanup is registered.

## 5. Architectural decisions made during implementation

- **One Postgres container per test** instead of `testutil`'s shared server. `PausePostgres` must freeze only that test's database, and a per-test deployment can't leak state between scenarios. It costs about 2 s per test.
- **Shortened timings in the harness** (TTL 3 s, heartbeat 1 s, tick 100 ms) keep recovery within seconds. The bounds scale to the production defaults.
- **Chaos runs on the test goroutine** in one loop that also polls completion. The harness helpers call `t.Fatal`, which must not run on another goroutine.
- **The soak DAG does about 3.3 s of work per run.** With very short tasks, 500 runs finished in 5 s, before any chaos fired.
- **Fixtures carry no `version`**, so re-registering one makes a new version. That lets the demo run twice against the same database.
- **The CLI uses stdlib `flag`**, so no dependency was added. Flags may come before or after positional arguments, and `-o` may appear anywhere.

## 6. Deviations from the specification

- **Recovery fallback (fix to 03.04):** see the `00A` amendment "ADR-007 amendment — 03.09".
  - **The defect:** a worker SIGKILLed and restarted under the same id re-registered while its lease was still live. Its dead incarnation's attempt then stayed `RUNNING` until the task deadline, 3600 s by default, because `ListOrphanedAttempts` skipped attempts of worker ids holding a lease.
  - **The fix:** the fallback abandons any attempt silent for 3×heartbeat + TTL. A live worker heartbeats every attempt it runs.
  - **The rejected alternative:** marking incarnations at `Register` would recover faster and keep all liveness in the `LeaseProvider` (a review finding). It needs a schema change, so it is left for 04.07's Raft leases (§7).
- **Scenario expectations corrected to the documented semantics.** These are not code changes:
  - **Timeout:** a cooperative handler's context ends just before the deadline and reports retryable `DEADLINE` (handlers.md), so the task ends `FAILED`. `TIMED_OUT` appears only when the scheduler's `TimeoutLoop` wins. The test accepts either and requires the failure within seconds.
  - **Rerun with `on_failure`:** a failure whose `on_failure` dependent succeeds is *handled*, so the run succeeds (workflow-semantics.md), and only a `FAILED` run can be rerun. The fixture's branch therefore escalates (fails), which fails the run. The rerun of the task then succeeds, skips the branch and runs the success path.
- **Phase-1 criteria source:** the v1.0 §19 text isn't in the repository. The gate uses the task file's own §5 mapping, plus FR-WF-09.
- **Additions beyond the list:** `TestWorkerRestartedWithSameID`, `TestCLIEndToEnd` and `TestDemoScript`.

## 7. Known limitations / follow-ups

- **Timeout status:** a timed-out task normally shows `FAILED` with error code `DEADLINE`, not `TIMED_OUT`. That matches handlers.md, but a user may expect `TIMED_OUT`. A follow-up could map a `DEADLINE` report to the timeout outcome.
- **Liveness altitude:** recovery's fallback reads attempt heartbeats from Postgres instead of asking the `LeaseProvider`. `LeaseProvider.Alive` is now unused in production but still tested. When 04.07 brings Raft leases, consider incarnation ids at `Register`.
- **The cron scenario waits for a real minute boundary** (up to 60 s), so the suite's time varies by up to a minute.
- **Timings come from one machine** (macOS, Docker Desktop). The CI job has a 30-minute limit; local runs take about 5 minutes.
- **`make sqlc-check` fails until the regenerated `sqlcgen/recovery.sql.go` is committed.**
- **Not run here:** the CI e2e job itself, since nothing has been pushed.
