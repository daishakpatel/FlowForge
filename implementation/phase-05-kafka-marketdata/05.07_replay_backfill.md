## 3. Objective

Provide operator- and workflow-invocable replay of historical data through the same pipeline code, using a dedicated consumer group, so aggregates can be rebuilt safely even while live processing continues.

## 4. Detailed Implementation Requirements

- `internal/stream/replay`: `ReplaySpec{ID, Mode(offset|timestamp|time_range), Partitions?, FromOffset?, FromTime, ToTime, Symbols[]?, DryRun}`; persisted in `market_replay_jobs` (status `pending|running|succeeded|failed|cancelled`, progress, counters, error).
- Runner uses a unique consumer group `flowforge-replay-<id>`, assigns partitions manually at the resolved start offsets (`ListOffsetsAfterMilli`), reads until the end offset **captured at start** (bounded job), filters by symbols/time, runs events through the *same* decode→persist→aggregate stages with a replay flag (no DLQ duplication of already-DLQ'd reasons? **decision:** replay DLQ writes are suppressed and counted), then forces recompute of touched windows.
- Safety with live traffic: dedupe + recompute-from-ticks make overlap harmless; replay never commits to the live group; replay writes are rate-limited (`FF_REPLAY_MAX_EVENTS_PER_SEC`).
- Interfaces: `flowforgectl replay start|status|cancel`, and a Go service API used by the `REPLAY_RANGE` task handler (05.10) and by the approved AI action `replay_range` (06.06). Idempotency by `replay_id` (re-submitting returns the existing job).
- Retention guard: if requested range is older than topic retention, job fails fast with a clear error and suggests loading from file source.

## 5. Technical Design

Replay determinism claim: replaying a fixed offset range into a **fresh** database yields byte-identical `market_aggregates` (excluding bookkeeping columns) as the original live run over the same events — verified by comparing a canonical dump hash.
Replay of a range while live processing runs yields the same final aggregates as live alone (idempotency), verified by a concurrent test.

**Design notes / edge cases:**

- Cancellation must stop promptly and leave data consistent (windows recomputed or untouched).
- Use `end offsets at start` so the job terminates even if the topic keeps growing.

## 8. Testing Requirements

- Replay determinism: live run hash == fresh-DB replay hash.
- Concurrent replay + live: final aggregates identical to live-only; no live offset commits by replay group (assert group offsets).
- Modes: by offset, by timestamp, by symbol subset, by time range → correct event counts.
- Cancel mid-run → status `cancelled`, windows consistent after follow-up recompute.
- Expired range → fast failure with message; idempotent submit returns same job.

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
