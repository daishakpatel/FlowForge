## 3. Objective

Expose market-data analytics and pipeline health through the FlowForge REST API and implement the monitoring primitives (lag, freshness, rates) plus the data-quality check logic used by the `market-data-quality-check` workflow task.

## 4. Detailed Implementation Requirements

- REST (viewer role) `GET /api/v1/marketdata/ohlcv?symbol&window&from&to&limit`, `GET /api/v1/marketdata/symbols`, `GET /api/v1/marketdata/freshness`, `GET /api/v1/marketdata/pipeline` (lag per partition, rates, queue depth, DB write latency p95, dedupe/late/DLQ counters, backpressure flag); OpenAPI + contract tests; pagination limits (max 1000 rows), time-range validation; read from Timescale via a read-only role/pool.
- Lag: computed from Kafka admin (`end offset − committed offset` for the processor group); freshness = `now − max(event_time)` per symbol and overall; cache 2 s to protect Kafka/DB.
- `internal/stream/quality`: `Check(spec) Report` — completeness (expected windows vs present given symbols & trading-hours config), staleness (> threshold), anomaly count, DLQ ratio, duplicate ratio, gap detection; thresholds configurable; returns structured findings with `severity`.
- Processor exposes `/stats` (internal) feeding the pipeline view; Prometheus gauges `flowforge_stream_lag{partition}`, `flowforge_stream_freshness_seconds{symbol}`, rates, queue depth, `flowforge_stream_db_write_seconds`.
- Internal read variants under `/internal/v1/marketdata/*` for the AI tools (role `ai-readonly`), returning the same payloads with tighter limits.

## 5. Technical Design

Metric label discipline: `symbol` label allowed only when the configured symbol universe ≤ 50 (config guard); otherwise freshness is reported as top-N worst symbols in the API, not as label cardinality.

**Design notes / edge cases:**

- API never exposes raw tick payloads beyond `limit`; no SQL built from user text (sqlc-generated queries).
- Quality check is pure given inputs from queries → unit-testable.
