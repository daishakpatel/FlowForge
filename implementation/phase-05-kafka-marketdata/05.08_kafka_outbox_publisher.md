## 3. Objective

Implement the Kafka-backed `Publisher` consumed by the outbox relay loop (03.07): publish workflow/task events as envelopes to the topic stored on each outbox row (`flowforge.workflow-events` or `flowforge.task-events`, per `00E §7`) keyed by `run_id` with at-least-once semantics, retries, DLQ for permanently failing rows, and lag/backlog metrics.

## 4. Detailed Implementation Requirements

- `internal/events/kafkapub`: implements `outbox.Publisher` (interface from 03.07) — maps outbox row to `flowforge.event.v1` envelope (event_id = outbox id, key=run_id, `traceparent` from stored context), validates schema, publishes with `acks=all`, returns per-row success so the relay marks only published rows.
- Relay integration: `FF_OUTBOX_PUBLISHER=kafka|noop` in `flowforge-scheduler` (leader-gated relay loop) and the dev default remains `noop` when Kafka absent.
- Failure handling: transient errors → relay retry with backoff (`attempts++`); permanent (`schema_invalid`, message too large) → after `FF_OUTBOX_MAX_ATTEMPTS` (default 10) move to `flowforge.dlq` and mark `dead`; metrics `flowforge_outbox_backlog`, `…_oldest_age_seconds`, `…_publish_failures_total`.
- Ordering: relay publishes rows for the same `run_id` in `id` order and does not advance past a failing row of that run (per-key head-of-line) while allowing other runs to proceed.
- A reference **consumer example** `cmd/flowforge-eventtail` (dev tool) printing events, plus a consumer-side idempotency helper keyed by `event_id` for downstream readers (AI may use it later).

## 5. Technical Design

Delivery semantics: at-least-once; duplicates possible when the relay crashes after publish and before marking. Consumers dedupe by `event_id` (documented). Per-run ordering preserved by key + head-of-line rule.

**Design notes / edge cases:**

- Do not hold the DB transaction while publishing; claim rows with `FOR UPDATE SKIP LOCKED` + `locked_until`, as in 03.07.
- Leadership change mid-batch: new leader may republish a batch → duplicates acceptable.

## 8. Testing Requirements

- Workflow run end-to-end: every transition event appears on its topic (`flowforge.workflow-events` or `flowforge.task-events`) once or more, with matching `event_id`s and per-run order.
- Crash after publish before mark → duplicates but no loss; consumer idempotency helper dedupes.
- Kafka down → backlog grows, relay resumes and drains after recovery; workflow execution unaffected (degraded matrix row).
- Permanent failure row → DLQ + `dead`, other rows continue.
- Head-of-line: failing row of run A does not block run B.

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
