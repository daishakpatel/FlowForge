## 3. Objective

Automate all twelve Raft failure scenarios from the original spec (§8.7) plus fencing scenarios, with expected-vs-observed documentation and linearizability checking. This is the gate for Phase 04.

## 4. Detailed Implementation Requirements

- Fault test suite under `test/fault/raft/` (tag `fault`): each scenario has `Expected` behavior defined in code (assertions) and writes a row into a machine-readable results file `docs/testing/raft-fault-results.json` (+ rendered `docs/testing/raft-fault-report.md`).
- Scenarios (map to v1.0 §8.7): (1) kill leader; (2) kill follower; (3) restart follower; (4) kill two nodes (writes rejected, reads per policy); (5) restore a node with stale local data (restore old data dir copy → must not violate safety: node catches up or refuses per identity/term checks); (6) network delay (Toxiproxy/FaultTransport latency spikes); (7) network partition (1|2 split: majority progresses, minority rejects); (8) restart all nodes (state preserved); (9) writes without quorum; (10) state-machine consistency after recovery (`StateHash` equal on all nodes at equal applied index); (11) snapshot restore of wiped node; (12) stale scheduler cannot act after new epoch (reuses 04.07 harness).
- Extra scenarios: rolling restart under load; leader transfer under load; clock-skew simulation (leader clock +2 s via injected clock): leases remain safe because of fencing; slow disk (artificial `fsync` delay via test storage wrapper) → elections remain stable or recover; large snapshot install under load.
- Linearizability: every scenario that runs a client workload records a history and runs the Porcupine KV model; histories archived on failure; add a *negative control* test (deliberately broken serializable-read-as-linearizable client) that Porcupine **detects** as non-linearizable, proving the checker works.
- Make target `make test-fault-raft` (Docker required for container-level scenarios; in-process variants run in CI by default, container-level in nightly workflow).

## 5. Technical Design

Report format (generated): table with columns `#, scenario, injected fault, expected, observed, pass/fail, time-to-recover (s), notes`. Time-to-recover is measured as the first successful linearizable write after the fault. Targets from master spec §6.1: Raft failover ≤ 3 s, scheduler failover ≤ 10 s — the report states measured values and whether targets were met; failing a target is reported honestly with analysis (not hidden).

Container-level faults use Docker (kill/stop/pause/network disconnect) via the Go Docker client or CLI wrapper in `test/fault/dockerctl`; network delay/partition uses Toxiproxy (add `toxiproxy` service to the `raft` profile fronting peer links) **or** `docker network disconnect` — pick one and document.

**Design notes / edge cases:**

- Every scenario must be deterministic enough to run 5× consecutively without flake; record observed variance.
- Use unique key prefixes per scenario to avoid cross-talk.
