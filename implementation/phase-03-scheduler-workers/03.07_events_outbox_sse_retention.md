## 3. Objective

Deliver reliable event publication via the transactional outbox (publisher-agnostic until Kafka arrives in 05.01), the Server-Sent Events stream used by the dashboard, and the retention/cleanup jobs.

## 4. Detailed Implementation Requirements

- `internal/outbox`: `Publisher` interface (`Publish(ctx, []Message) error` where `Message{Topic, Key, Value, Headers}`); implementations `LogPublisher`, `MemoryPublisher` (tests). Kafka implementation is added in 05.01 and selected by config `FF_EVENT_PUBLISHER=log|kafka|none` (default `log` in dev).
- `outbox.RelayLoop` (leader-gated): reads unpublished rows in id order (batch ≤ 500, `FOR UPDATE SKIP LOCKED` to be safe), publishes, then sets `published_at` for the **successfully published prefix**; on error retry with capped backoff; guarantee at-least-once and per-key (run) ordering. Metrics: `flowforge_outbox_backlog`, `flowforge_outbox_publish_lag_seconds`, publish error counter.
- SSE endpoint `GET /api/v1/events/stream` (viewer): query `run_id`, `types`, `since` ; honors `Last-Event-ID` (the `workflow_events.id`); emits `id: <n>\nevent: <event_type>\ndata: <envelope json>\n\n`; polls the table every 500 ms **and** wakes on `LISTEN ff_events` (events `NOTIFY ff_events` is sent by `events.Record` at commit — add `pg_notify` inside the same transaction); keep-alive comment every 15 s; max concurrent streams `FF_SSE_MAX_CONNECTIONS` (200) → 503 beyond; per-connection slow-client protection (drop connection if write blocks > 10 s); not subject to the global request timeout.
- `retention.Loop` (leader-gated, hourly): delete published `outbox` rows older than 3 d, `workflow_events` > 30 d, `task_logs` > 14 d (batches of 5 000 with sleeps), and `UPDATE workflow_runs SET idempotency_key=NULL` for runs older than 24 h. Config overrides `FF_RETENTION_*`. Metric for rows deleted.
- Event query endpoint `GET /api/v1/runs/{id}/events` (from 02.04) gets cursor by event id for consistency with SSE.

## 5. Technical Design

```mermaid
flowchart LR
  tx[state transition tx] -->|insert| ev[(workflow_events)]
  tx -->|insert| ob[(outbox)]
  tx -->|pg_notify ff_events| N((NOTIFY))
  relay[Relay loop - leader] --> ob
  relay -->|Publish| pub[Publisher: log | kafka]
  ev --> sse[SSE handler] --> ui[Dashboard]
  N --> sse
```
Relay failure semantics: publish succeeds, DB update fails → rows re-published later → consumers dedupe on `event_id` (documented in `00E §7`). Publish fails → nothing marked; ordering preserved because the batch is retried from the first unpublished id.

SSE reads from Postgres, not Kafka, so the dashboard works with Kafka down.

**Design notes / edge cases:**

- Do not use one pg connection per SSE client for LISTEN — a single shared listener fans out to subscribers.
- Retention deletes must never block hot tables: bounded batches, `ORDER BY id LIMIT`, sleeps between batches.

## 8. Testing Requirements

- Relay: 1 000 events with a publisher failing every 7th batch → every event eventually published ≥ 1 time; per-run order preserved; `published_at` only on published prefix.
- Relay crash: kill relay between publish and mark → on restart duplicates published but `event_id`s identical (test counts duplicates, asserts dedupe by id restores exactly-once-view).
- SSE: client receives events for a started run in order; reconnect with `Last-Event-ID` receives only newer events (no gaps/dupes); filter by `run_id`; 201st connection → 503; keep-alive observed.
- SSE latency: transition → client receipt p95 < 1 s (measured with NOTIFY).
- Retention: seeded old rows deleted in batches; recent rows kept; idempotency key nulled for 25 h-old run, kept for 1 h-old.
- Leader gating: relay does nothing when Gate not leader.

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
