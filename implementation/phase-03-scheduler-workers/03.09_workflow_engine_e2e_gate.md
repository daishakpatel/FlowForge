## 3. Objective

Close the workflow-engine milestone: ship the `flowforgectl` CLI and an end-to-end test suite (real Postgres, real binaries or in-process equivalents) proving the Phase-1 acceptance criteria, including crash/restart and soak scenarios. **Do not start Phase 04+ integration work until this gate passes.**

## 4. Detailed Implementation Requirements

- `cmd/flowforgectl` (stdlib `flag`/`cobra`): commands `workflows create -f file.json`, `workflows list|get`, `runs start <workflow> [--input file] [--idempotency-key k]`, `runs get|tasks|events|logs <id>`, `runs watch <id>` (SSE), `runs cancel|pause|resume|rerun|retry`, `workers list`, `triggers create|list|enable|disable`, `api-keys create|list|revoke`; config `FF_API_URL`, `FF_API_KEY`; JSON (`-o json`) and table output; non-zero exit on API errors with the error envelope printed.
- `test/e2e` harness: starts Postgres (testcontainers), runs `flowforge-api`, `flowforge-scheduler`, N `flowforge-worker` **as real subprocesses** (built binaries) with random ports; helpers to kill -9, restart, pause (SIGSTOP/SIGCONT), and to stop/start Postgres via Docker; waits via `Eventually`.
- Scenario library (each its own test with the fixture definitions in `test/fixtures/workflows/*.json`): diamond DAG across 2 workers; parallel fan-out respects capacity; retry-then-succeed (`flaky`); non-retryable failure; timeout; worker SIGKILL mid-task → reassigned; worker SIGSTOP/SIGCONT zombie → stale rejection; scheduler restart mid-run; API restart mid-run; DB pause for 5 s; cancel; pause/resume; rerun after failure with `on_failure` branch; templating chain; cron trigger firing; idempotent run start; SSE consumption.
- **Soak/invariant test**: 500 runs × 6-task DAG with 4 workers and a chaos goroutine (random worker kill every 10 s, scheduler restart every 30 s) → all runs reach terminal states; for every task the number of attempts with `status=SUCCEEDED` is ≤ 1; DB invariants (`AssertInvariants`) hold; total duration recorded.
- Phase gate report `docs/testing/phase3-gate.md`: table of Phase-1 acceptance criteria from v1.0 §19 mapped to test names and pass/fail with timings. Include the measured recovery times (worker-loss, scheduler restart).
- Demo fixtures: `test/fixtures/workflows/{diamond,retry,market-data-skeleton}.json` and a script `scripts/demo/engine-demo.sh` using `flowforgectl` to show a run.

## 5. Technical Design

The harness must run in CI (`make test-e2e`, tag `e2e`, ~10 min budget) and locally. Subprocess logs are captured per test and attached on failure. Ports are allocated dynamically. Binaries are built once per test run.

Acceptance mapping (v1.0 Phase 1): multi-step DAG completes → *diamond*; failed task retries per policy → *retry-then-succeed*; scheduler restart doesn't lose pending state → *scheduler restart*; worker restart handled without corruption → *worker SIGKILL*; invalid DAGs rejected → CLI `workflows create` of cyclic fixture exits non-zero with `CYCLE`.

**Design notes / edge cases:**

- If subprocess execution is impossible in the agent sandbox, run the same scenarios with in-process services and state so in the report; the soak/chaos test must still run in-process with simulated kills (cancel contexts) — document the weaker guarantee.
- Keep tests deterministic where possible; chaos soak uses a seeded RNG and logs the seed.

## 6. Step-by-Step Implementation Instructions

1. Implement `flowforgectl` with a thin typed client (reuse generated OpenAPI types if available, otherwise hand-written minimal structs) and tests against `httptest`.
2. Build the e2e harness (process manager, fault helpers, log capture).
3. Write fixtures and scenarios one by one; stabilize flakiness (no sleeps; use `Eventually`).
4. Write the soak/chaos test; run it at least 3 times; record seeds/durations.
5. Write the gate report and demo script.
6. Fix any defects found in earlier tasks via minimal compatible changes (list in report under *Follow-ups/Deviations*).
