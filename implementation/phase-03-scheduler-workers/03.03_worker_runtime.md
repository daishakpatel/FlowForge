## 3. Objective

Implement `flowforge-worker`: a pull-based worker with a handler registry, bounded concurrency, heartbeats, fenced result reporting, log shipping, cooperative cancellation and graceful shutdown; plus built-in demo handlers used by tests and the demo.

## 4. Detailed Implementation Requirements

- `cmd/flowforge-worker/main.go` (config via `FF_WORKER_*`, `FF_API_GRPC_TARGET`, `FF_WORKER_TOKEN`).
- `internal/worker/runtime`: gRPC client with reconnect/backoff, `Register` on start and on reconnect, heartbeat loop (`FF_WORKER_HEARTBEAT`, default 5 s), poll loop honoring free capacity (semaphore), per-attempt goroutine with a context bounded by the attempt deadline (courtesy enforcement) and cancelled by cancel/stale signals.
- Handler SDK `internal/worker/handlers`: `type Handler interface{ Type() string; Execute(ctx context.Context, tc TaskContext) (json.RawMessage, error) }`; `TaskContext{TaskID, AttemptID, AttemptNumber, IdempotencyKey, Input, Deadline, Logger, RunID, Traceparent}`; `Registry.Register(h)`; errors: `handlers.NonRetryable(code, err)`, `handlers.Retryable(code, err)`, default (unclassified) = retryable `HANDLER_ERROR`; panics recovered → retryable `PANIC` with stack trace in logs only.
- Result reporting: `CompleteTask`/`FailTask` with the fencing token; on `STALE_ATTEMPT` response cancel the handler context (if still running), log WARN, and **never retry reporting**; transient transport errors retry with backoff until the attempt deadline.
- Cancellation: heartbeat response `cancel_attempt_ids` → cancel that attempt's context; handler returning `context.Canceled` is reported via `FailTask(error_code="CANCELLED", retryable=false)`; `stale_attempt_ids` → cancel and drop result.
- Log shipping: per-attempt `TaskContext.Logger` writes structured lines to a bounded channel → `ShipLogs` stream (drop-oldest on overflow, count drops); flush on completion.
- Graceful shutdown (SIGTERM): stop polling, wait up to `FF_WORKER_SHUTDOWN_GRACE` (default 30 s) for running attempts, then cancel their contexts, report outcomes, `Deregister`. Metrics: `flowforge_worker_active_tasks`, task outcome counters.
- Built-in handlers: `noop` (returns input), `sleep` (`{"duration_ms"}` honoring ctx), `fail` (`{"code","retryable"}`), `flaky` (fails while `attempt_number <= fail_attempts`), `echo`, `crash` (calls `os.Exit(1)` — enabled only when `FF_WORKER_ENABLE_CRASH_HANDLER=true`, for chaos tests).

## 5. Technical Design

```mermaid
flowchart LR
  poll[poll loop] -->|free capacity>0| api[(WorkerService)]
  api --> task[Task]
  task --> exec[attempt goroutine: handler.Execute(ctx)]
  exec --> rep[Complete/Fail with fencing token]
  hb[heartbeat loop] --> api
  api -->|cancel_ids / stale_ids| hb --> exec
```
Concurrency model: one semaphore of size `capacity`; polls request `free_capacity = capacity - active`. Deadline: `ctx` with deadline = task deadline − 1 s margin; *the server's timeout decision is final* (ADR-021) — a worker that overruns will find its attempt TIMED_OUT and its report rejected.

Handlers with external side effects MUST use `TaskContext.IdempotencyKey`. Document this prominently in `docs/architecture/handlers.md` with a worked example (idempotent insert with unique key).

**Design notes / edge cases:**

- Heartbeat must continue while handlers block; run it in its own goroutine and never share locks with handlers.
- On API unavailability the worker continues executing running attempts, buffers results (bounded) and retries until deadlines — matches the degraded matrix in the master spec §6.2.
- goleak must pass: no goroutines left after shutdown.

## 8. Testing Requirements

- Integration: `noop` task completes; result persisted; attempt SUCCEEDED; events recorded.
- Capacity: `capacity=2`, 10 `sleep` tasks → never more than 2 RUNNING for that worker (sampled via DB).
- Failure paths: handler error → attempt FAILED with code/retryable flag; panic → `PANIC`; non-retryable classification propagates.
- Cancellation: heartbeat returns a cancel id → handler context cancelled within 2 heartbeat intervals; reported as CANCELLED.
- Stale: after the attempt is flipped to ABANDONED server-side, worker completion is rejected and handler ctx cancelled; no retry of the report.
- Reconnect: API restarted mid-run → worker re-registers, keeps running attempt, reports result successfully.
- Graceful shutdown: SIGTERM with in-flight 2 s task and 5 s grace → completes, deregisters, exit 0; with 100 ms grace → cancels and reports.
- Logs: lines from handler appear via `GET /attempts/{id}/logs`; overflow drops oldest and increments a counter.
- goleak clean after shutdown.

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
