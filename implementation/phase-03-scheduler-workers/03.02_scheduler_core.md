## 3. Objective

Implement `flowforge-scheduler` and its core loop: promote tasks PENDING→READY/SKIPPED→QUEUED according to dependency/`run_if` semantics and concurrency limits, drive run status transitions, behind a leadership `Gate` abstraction (always-leader for now) with epoch assertion on every decision transaction.

## 4. Detailed Implementation Requirements

- `cmd/flowforge-scheduler/main.go`: config, logger, pg pool, loop registry, obs server, graceful shutdown.
- `internal/scheduler`: `Gate` interface (`IsLeader() bool`, `Epoch() int64`, `Done() <-chan struct{}` closed on leadership loss, `Wait(ctx)`), `AlwaysLeader` implementation (epoch 0), `Loop` interface (`Name() string`, `Run(ctx, gate) error`), `Runner` that starts all registered loops only while the Gate says leader and cancels them promptly on loss (≤ one tick).
- `SchedulerLoop` (tick `FF_SCHED_TICK`, default 500 ms; also woken by `LISTEN ff_scheduler_wake` which API/workers `NOTIFY` after completions): selects up to 200 runs in `CREATED|RUNNING` ordered by `updated_at` (fairness), and for each runs `processRun` in its own transaction.
- `processRun(tx)`: `AssertEpoch`; load **head** task instances of the run (a task row not superseded by another — see Notes) as `TaskView`s; (1) `CREATED→RUNNING` (+`started_at`, `run.started`); (2) for each PENDING task evaluate `statemachine.EvaluateReadiness` (expression evaluator seam, nil for now) → `READY` or `SKIPPED`; (3) promote READY→QUEUED subject to limits; (4) when all head tasks terminal derive run status via `statemachine.DeriveRunStatus` → terminal status, `completed_at`, event `run.succeeded|failed|needs_attention`; (5) `NOTIFY ff_task_queued` if any task was queued.
- Concurrency limits: per-run `concurrency.max_parallel_tasks` (QUEUED+RUNNING count) and global per-queue limits from config `FF_QUEUE_LIMITS` (`queue=n,queue2=m`, default unlimited); promotion order: oldest `available_at` first, then task creation order.
- Input resolution seam: `InputResolver.Resolve(ctx, run, task, deps) (json.RawMessage, error)`; default copies `config` verbatim as `input` (03.06 replaces with templating); resolver error → task `FAILED` non-retryable `INVALID_INPUT` (recorded as attempt-less failure with event).
- Loop metrics (`flowforge_scheduler_tick_duration_seconds`, `flowforge_scheduler_queue_depth{queue}`, `flowforge_tasks_total{status}`, `flowforge_workflows_started_total`, `flowforge_workflows_completed_total{status}`, `flowforge_workflow_duration_seconds`) per `00E §11`.

## 5. Technical Design

```mermaid
flowchart TD
  tick[tick / NOTIFY] --> sel[select runs CREATED|RUNNING]
  sel --> tx{{tx per run}}
  tx --> ae[AssertEpoch]
  ae --> load[load head tasks]
  load --> ready[PENDING → READY / SKIPPED]
  ready --> q[READY → QUEUED within limits]
  q --> fin{all terminal?}
  fin -->|yes| derive[DeriveRunStatus → terminal + events]
  fin -->|no| done[commit + NOTIFY]
  derive --> done
```
**Idempotency by construction:** every promotion is a conditional update (`WHERE status = from`); re-running a tick after a crash re-evaluates the same inputs and either finds work already done (0 rows → ignored as `INVALID_STATE` benign) or does it. The loop treats `INVALID_STATE` from a promotion as "someone else/previous attempt did it" and continues.

`Gate` contract: loops must never make a decision after `Done()` is closed; all DB decisions assert the epoch in-tx (belt and braces). `AlwaysLeader` exists so single-scheduler mode works with no Raft (this remains a supported dev mode).

**Design notes / edge cases:**

- **Head instance rule (needed by 03.06):** treat a task as *head* iff no other row has `supersedes_task_id = task.id`. Implement the query now (`NOT EXISTS`), even though no rerun exists yet, so 03.06 only adds rows.
- Do not load all tasks of all runs into memory: query per run, bounded by 500 tasks (definition limit).
- Fairness: a slow giant run must not starve others — per-tick cap of 200 runs and ≤ 100 promotions per run per tick.
- Paused runs (03.05) are skipped for promotions; leave a `if run.Status == PAUSED { continue }` seam with test placeholder.

## 8. Testing Requirements

- Unit: Runner starts loops on leadership gain, cancels within one tick on loss, restarts on regain (fake Gate + fake clock).
- Integration: linear and diamond DAG progress as test code manually completes tasks (QUEUED→RUNNING→SUCCEEDED via repos): downstream task becomes READY only after all deps SUCCEEDED.
- Integration: `on_failure` branch is SKIPPED when parent succeeds; READY when parent FAILED; run SUCCEEDED/FAILED per `DeriveRunStatus` (handled-failure rule).
- Integration: `max_parallel_tasks=2` never exceeds 2 QUEUED+RUNNING; queue limit config honored.
- Fuzz: seeded random DAGs (200 runs, total ≈ 10 000 tasks, widths 1–20) driven to completion by a simulated executor: every task queued **exactly once** (event count), no task QUEUED before deps terminal, all runs terminal with expected status.
- Idempotency: run `processRun` twice concurrently on the same run (two goroutines) → no duplicate events, no errors surfaced.
- Epoch: with `cluster_state.epoch=7` and scheduler epoch 3 → no decision committed (loop logs `STALE_EPOCH` and stops).

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
