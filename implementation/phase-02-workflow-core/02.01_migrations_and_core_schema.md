## 3. Objective

Establish the goose-based migration system and create the canonical `flowforge` schema (migrations 0001–0004) exactly as specified in `00E §2`, plus the sqlc scaffold.

## 4. Detailed Implementation Requirements

- Add `migrations/flowforge/` with goose SQL files `0001_core.sql`, `0002_events_outbox_logs.sql`, `0003_workers_security.sql`, `0004_triggers_approvals.sql` copied **verbatim** from `00E §2` (add `-- +goose Up` / `-- +goose Down` markers; Down may be a documented no-op comment — policy is forward-only, Down is only used by tests to reset).
- `internal/persistence/migrate`: embeds migration directories (`//go:embed`), exposes `Up(ctx, dsn, set)`, `Status`, `Version`; supports sets `flowforge` and `marketdata` (marketdata directory may be empty until 05.03).
- `cmd/flowforge-migrate`: CLI (`flowforge-migrate --db flowforge|marketdata up|status`) reading DSNs from config (`FF_PG_DSN`, `FF_MD_PG_DSN`).
- Makefile: `migrate-up`, `migrate-status`; implement `testutil.ApplyMigrations(t, dsn, set)` (stubbed in 01.02) and add helpers `testutil.NewFlowforgeDB(t)` = ephemeral DB with migrations applied.
- `sqlc.yaml` configured for engine `postgresql`, pgx/v5, schema from `migrations/flowforge`, queries from `internal/persistence/queries/`, output `internal/persistence/sqlcgen` (package `sqlcgen`); `make sqlc` runs it; add one trivial query (`GetClusterState`) to prove the pipeline; CI drift check (`make sqlc && git diff --exit-code`).
- Schema tests asserting tables, columns, CHECK constraints, unique/partial indexes, the `attempt_fencing_seq` sequence and the seeded `cluster_state` row exist.

## 5. Technical Design

Migrations are forward-only and idempotently runnable (goose tracks versions). They run: (a) explicitly via `flowforge-migrate`, (b) automatically in tests, (c) in Compose via an init job (wired in 09.02). Services never auto-migrate in production mode; `flowforge-api` checks the schema version at startup and refuses to start if it is behind (`ErrSchemaBehind`) — implemented in 02.04 using `migrate.Version`.

Do not alter DDL from `00E §2`. If you believe a column/index is wrong, stop and raise via the deviation procedure (a corrected migration `0005_*` is the *only* acceptable way once merged).

**Design notes / edge cases:**

- `workflow_tasks` UNIQUE `(run_id, task_key, supersedes_task_id)` treats NULLs as distinct in Postgres; add a partial unique index `(run_id, task_key) WHERE supersedes_task_id IS NULL` in migration `0001` (documented small addition to `00E §2`; update `00E` accordingly) so original task keys remain unique per run.
- Verify the migration works on the pinned Postgres 16 image; avoid extensions in `flowforge` DB.
