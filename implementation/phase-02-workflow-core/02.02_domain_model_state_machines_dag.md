## 3. Objective

Implement the database-free core of the workflow engine: the workflow definition model with strict JSON decoding, the explicit task/attempt/run state machines, run-status derivation, and the DAG validator. This is the most test-heavy pure-logic task; everything later builds on it.

## 4. Detailed Implementation Requirements

- `internal/workflow/model`: `Definition`, `TaskDef`, `RetryPolicy`, `Concurrency`, enums (`TaskStatus`, `AttemptStatus`, `RunStatus`, `RunIf`) with the exact string values from `00E §2/§3`; `Decode([]byte) (*Definition, error)` using `DisallowUnknownFields`; default application (queue `default`, retry `max_attempts=1`, strategy `fixed`, `run_if=on_success`, timeouts) — defaults are explicit constants.
- `internal/dag`: `Validate(def) []ValidationIssue` returning *all* problems (code, task id, message) — duplicate IDs, id regex, unknown dependency, self-dependency, cycle (with the cycle path), >500 tasks, invalid retry (attempts 1–20, delays, multiplier ≥ 1, jitter 0–1, max_delay ≥ initial), invalid timeouts (1–86400), missing/blank type, invalid queue name, `run_if` invalid, `run_if=expr` with empty expression (hook `ExprValidator func(string) error` settable by 03.06), `run_if` that references (in expression text-hook) non-ancestors, workflow-level `timeout_seconds` bounds, invalid `on_failure` enum, invalid `concurrency.max_parallel_tasks`.
- `dag.TopoOrder(def)`, `dag.Ancestors(def, id)`, `dag.Roots(def)`, `dag.Children(def)` helpers with O(V+E) complexity.
- `internal/workflow/statemachine`: `CanTaskTransition(from,to) bool`, `CanAttemptTransition`, `CanRunTransition` driven by table data identical to `00E §3.1–3.3`; `TaskTransitionEvents(from,to) EventType`; `IsTerminal*`; `ErrInvalidTransition` wrapping `apperrors.InvalidState`.
- `statemachine.DeriveRunStatus(tasks []TaskView, def policy) RunStatus` implementing `00E §3.3–3.4` including the **handled-failure rule** (a failed task is handled if some dependent with `run_if` ∈ {on_failure, always, expr} SUCCEEDED).
- `statemachine.EvaluateReadiness(task TaskView, deps []TaskView) ReadinessDecision` (`Ready|Skip|Wait`) implementing `run_if` semantics (expression evaluation delegated to an injected `ExprEvaluator`, nil → treated as error for `expr`).
- `statemachine.NextRetryDelay(policy, attemptNumber, rng) time.Duration` — exponential with multiplier, cap, jitter (full jitter bounded ±jitter fraction), deterministic with injected `*rand.Rand`.

## 5. Technical Design

Transition table (source of truth is `00E §3.1`; encode as data, not nested ifs):

```go
var taskTransitions = map[TaskStatus]map[TaskStatus]struct{}{
  Pending:   {Ready:{}, Skipped:{}, Cancelled:{}},
  Ready:     {Queued:{}, Cancelled:{}},
  Queued:    {Running:{}, Cancelled:{}},
  Running:   {Succeeded:{}, RetryWait:{}, Failed:{}, TimedOut:{}, Cancelled:{}},
  RetryWait: {Queued:{}, Cancelled:{}},
}
```
`DeriveRunStatus` outline:
1. any task non-terminal → `RUNNING` (or `PAUSED`/`CANCELLED` is decided by run flags outside this function).
2. all terminal: compute `unhandledFailures` = tasks FAILED/TIMED_OUT with no SUCCEEDED handling dependent.
3. unhandledFailures empty → `SUCCEEDED`; else `def.on_failure == needs_attention` → `NEEDS_ATTENTION` else `FAILED`.

Retry delay: `base = min(max_delay, initial * multiplier^(n-1))` (fixed strategy: `initial`); `delay = base * (1 + jitter*u)` where `u ∈ [-1,1]` from rng; never below 0, never above `max_delay*(1+jitter)`.

Validation issue codes (stable, used by API `details[]` in 02.04): `DUPLICATE_TASK_ID, INVALID_TASK_ID, UNKNOWN_DEPENDENCY, SELF_DEPENDENCY, CYCLE, TOO_MANY_TASKS, INVALID_RETRY, INVALID_TIMEOUT, MISSING_TYPE, INVALID_QUEUE, INVALID_RUN_IF, EMPTY_EXPRESSION, INVALID_WORKFLOW_FIELD`.

**Design notes / edge cases:**

- Cycle detection via Kahn's algorithm; on failure, extract one concrete cycle path with DFS over the leftover nodes for the error message.
- Validation must be deterministic: sort issues by (task id, code).
- No imports of DB/HTTP/grpc packages (lint-enforced in 01.01).

## 6. Step-by-Step Implementation Instructions

1. Define model types and strict decoding with defaults; table-test decoding (unknown field rejected, defaults applied).
2. Implement graph helpers and `Validate`; write the ≥ 25-case validation table including every issue code, multi-issue aggregation and boundary values.
3. Encode transition tables and write an exhaustive matrix test: for every (from,to) pair of every machine assert allowed/denied exactly as `00E §3`.
4. Implement `EvaluateReadiness` and `DeriveRunStatus`; table-test every `run_if` combination and handled/unhandled failure scenarios.
5. Implement `NextRetryDelay`; property-test bounds with seeded RNG over 10 000 samples.
6. Benchmark `Validate` on a 500-task DAG (wide, deep, dense-ish) — record result.

## 8. Testing Requirements

- Validation table: ≥ 25 cases; each issue code produced by at least one case; multiple issues aggregated; deterministic order.
- Cycle tests: 2-cycle, 3-cycle, self-loop (reported as SELF_DEPENDENCY), cycle in a disconnected component; reported path is a real cycle.
- Limits: 500 tasks accepted, 501 rejected; benchmark validates 500-task DAG < 100 ms.
- Transition matrix: exhaustive, compares against an independent literal copy of `00E §3.1` in the test (so a typo in code is caught).
- `DeriveRunStatus`: all-success, unhandled failure, handled failure (on_failure branch succeeded), handled failure but handler failed, `needs_attention` policy, skipped tasks.
- `EvaluateReadiness`: on_success/on_failure/always with every dependency-status combination; expr with nil evaluator errors.
- Retry delay: fixed vs exponential schedule exact values with jitter=0; with jitter, within bounds; capped at max_delay.

General: `make lint` and `make test` must pass; run packages you touched with `-race`; record exact commands and results in the completion report.
