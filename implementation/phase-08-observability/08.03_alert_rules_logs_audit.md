## 3. Objective

Define alert rules for the failure modes that matter, verify them with promtool unit tests, and audit structured logs for required correlation fields and redaction across all services.

## 4. Detailed Implementation Requirements

- `deploy/prometheus/alerts.yml` with severity, runbook links (`runbook_url` → `docs/runbooks/*.md`) and annotations: SchedulerNoLeader, SchedulerLeaderFlapping, RaftNoLeader/QuorumLost, RaftCommitLag, WorkerLeaseExpirySpike, TaskFailureRateHigh, OutboxBacklogGrowing/OldestAge, KafkaConsumerLagGrowing, MarketDataStale, StreamBackpressureSustained, DLQRateHigh, DBLatencyHigh/PoolExhausted, AIServiceDown, ApprovalsPendingTooLong, ServiceDown (up==0).
- `promtool test rules` unit tests under `deploy/prometheus/tests/*.yml` simulating series for each alert (fires and does-not-fire cases).
- Alertmanager (profile `observability`) with a local webhook sink (log) for demo; route by severity.
- Log audit: JSON logs of every service contain `ts, level, msg, service, request_id|trace_id, run_id|task_id|attempt_id` where applicable; `scripts/ci/check-logs` runs the e2e scenario and validates log lines against a JSON schema (field presence by context), checks redaction (seeded secrets `ff_…`, `password=` never appear in any service's logs or in the AI service logs), and verifies `trace_id` matches the active span.
- Gate: `make observability-check` aggregates catalogue check, dashboard check, promtool tests, log audit.

## 5. Technical Design

Alert design principles (documented): alert on symptoms with runbooks, not on every cause; multi-window for burn/lag growth; `for:` durations tuned to failover times measured in 04.08 (e.g. NoLeader for 15 s) to avoid flapping.

**Design notes / edge cases:**

- Each alert must map to an existing or newly added runbook (check script).
- Seed secrets in tests are fake, clearly marked.
